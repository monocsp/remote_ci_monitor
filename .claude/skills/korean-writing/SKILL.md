# korean-writing: 한국어 산출물을 처음부터 사람 말로 쓰는 규칙

이 스킬은 고치는 스킬이 아니라 쓰는 스킬이다. 사람이 읽을 한국어를 쓰기 직전에 로드해서 아래 규칙대로 쓴다.

이 레포에서 대상은 다음과 같다. 커밋 제목의 한국어 요약과 커밋 본문, PR 제목의 요약과 PR 본문, `PLAN.md` 와 `docs/` 아래의 한국어 계획서·작업 명세·리뷰 문서, 하위 에이전트에 주는 한국어 프롬프트, 사용자에게 하는 채팅 보고다. 웹 UI 의 한국어 문구도 사람이 읽는 글이라 §3 을 지킨다.

fluent-korean 원문(§2 「동작 범위」 2번)은 커밋 메시지를 코드에 속하는 텍스트로 보고 프로젝트 관례에 맡긴다. 이 레포의 관례는 커밋 본문과 PR 본문을 한국어 산문으로 쓰는 것이다(CONTRIBUTING.md 「Names」). 오너는 2026-11-19 에 그 산문을 이 스킬로 쓰라고 정했다. 그래서 커밋 제목의 형식은 commit 스킬과 `tools/guard_naming.py` 를 따르고 요약과 본문의 문장은 이 스킬을 따른다.

코드와 식별자, 인용문, 영어로 쓰는 문서(README, `docs/` 의 영어 문서, CHANGELOG, CLI 도움말)는 대상이 아니다. 코드 주석은 §2 「동작 범위」 2번에 따라 프로젝트 관례를 따른다. 이 레포의 관례는 주석과 docstring 을 한국어로 쓰는 것이다(AGENTS.md). 다만 §4 의 한자 표기 금지는 새로 쓰는 주석에도 적용한다.

세션의 설정 폴더가 `CLAUDE_CONFIG_DIR` 로 옮겨져 있으면 `~/.claude` 대신 그 폴더를 본다. 이 머신의 세션 설정 폴더는 `skills/` 만 `~/.claude/skills` 로 이어 두었다. 그 폴더에도 위의 도구는 없다.

판정 순서는 이렇다. 새로 쓰는 글이면 이 스킬을 따른다. 짧으면 직접 쓰고 길면 `korean-writer` 에게 넘긴다. 이미 쓰인 글을 고치는 일이면 `humanize-korean` 이다.

쓰는 층을 따로 두는 이유가 있다. 초안을 쓴 뒤 윤문으로 걷어내면 고칠 글이 이미 나쁜 구조로 굳어 있다. 그러면 윤문이 의미를 흔들고 커밋 본문 한 줄에도 파이프라인 비용이 붙는다. 처음부터 규칙대로 쓰면 고칠 것이 거의 남지 않는다.

## 2. fluent-korean 원문(요약하지 말고 예시까지 읽는다)

아래는 fluent-korean 의 `fluent-korean.md`(코딩 지침 유지판) 본문을 그대로 옮긴 것이다. 원문이 요약하지 말라고 적어 둔 이유가 본문 안에 있다. 대괄호 안의 화살표 예시가 각 조항이 정확히 어떤 동작을 뜻하는지 정한다. 이 절을 바꿀 때는 §8 갱신 절차를 따른다.

당신은 한국어를 활용해야 하는 상황에 있다면 본 문서에 제시된 지침들을 준수해야 합니다. 그럼으로써 의사소통의 효율성을 높일 수 있습니다. 이 지침들은, 의미가 명확하며 비교적 가독성이 높고 안정적인 구조를 지닌 한국어 문장을 출력하는 방법을 자세히 설명합니다. 인용, 코드, 코드 주석에는 이 지침들을 적용하지 않습니다.


### 상황과 목표

- LLM은 한국어를 구사할 때 몇 가지 특징을 보이는데, 일부 특징은 결과물의 완성도를 낮추거나, 사용자가 소통에 더 많은 노력을 들이게 만듭니다. 이 문서에 작성된 사항들을 준수하면 이런 현상을 개선할 수 있습니다.

- 이 문서에서 제시하는 지침들을 요약하는 것은 일반적으로 권장되지 않습니다. 그렇게 한다면 조항마다 첨부된 예시를 확인할 수 없으므로 조항의 문구가 구체적으로 어떤 동작을 의도했는지 파악하기 어렵습니다. 또한 요약에 포함된 몇 가지 지침을 제외한 나머지 지침들은 잘 준수되지 않는 방향으로 서술 압력이 작동하게 될 수도 있습니다. 그리고 목적과 의도를 생략하고 제한 사항만 요약한다면 목적에 부합하지 않게 기계적으로 지침을 준수했는지 확인하게 될 수도 있습니다.


### 동작 범위

1. 본문의 지침들은 한국어를 활용하는 상황에서 그 한국어를 명확하게 출력하라는 지시입니다. 외국어 문장이나 어휘를 출력해야 하는 상황에서, 그것을 한국어로 번역하거나 대체하라는 지시가 아닙니다.

2. 변수명과 주석, 커밋 메시지, 로그 문자열처럼 코드에 속하는 텍스트는 프로젝트의 기존 관례를 준수해야 합니다. 이러한 텍스트는 지침을 적용하면 안 되기 때문에 이 조항에서 한 번 더 강조하고 있습니다.

3. 고유 명사와 기술 용어 등은, 통상적인 용례로 정착된 번역어 혹은 음차가 있다면 우선적으로 사용하고, 그렇지 않다면 원어를 유지함으로써, 한국어 사용자가 이해하기 편하고 의미를 잘 이해할 수 있도록 합니다.

4. 사용자가 어떤 어조나 어휘를 사용하든지, 사용자 메시지의 어조를 모방하지 않고, 본문에서 제시하는 지침들을 일관되게 유지합니다.


### 문장 단위

1. 읽는 이가 문장의 의미를 충분히 이해할 수 있어야 하므로, 의미가 있는 문장 성분을 생략하지 않습니다. [그러면 경고가 붙습니다.→ ('그러면 이미 작업 중인 파일에도 경고 표지가 추가됩니다.'와 같이, 맥락과 정보를 충분히 제공하도록 수정) ]  특히 관형격 조사인 '~의'를 필요 이상으로 사용한다면, 의미를 담고 있는 문장 성분을 생략하기 쉬우므로 유의해야 합니다.  [사본의 문구는 작업의 상황을 → 사본에 기재된 문구는 작업이 진행되는 상황을]

2. (이 2번 조항은 헤더와 목록에는 강제로 적용되는 사항이 아닙니다.) 명사구나 부사구, 연결어미로 문장을 끝내지 말고, 서술어와 종결어미를 사용하여 완성된 형태의 문장으로 끝을 맺어야 합니다.


### 구 단위

1. 필수적인 경우가 아니라면 조사와 어미를 생략하지 말아야 합니다. 또한 부사, 보조사와 선어말어미, 보조 용언을 적극적으로 활용하면, 의미가 명확한 한국어 문장을 완성할 수 있습니다. [이 결정은 이후 중요 정책이 갈리는 자리. 컨텍스트 압축 전 신중 반영한다. → 이 결정은 이후 중요한 정책에 지속적으로 영향을 주기 때문에, 컨텍스트가 압축되기 전에 신중히 반영합니다. → 지금 답변해주신 결정 사항은 이후 중요한 정책에도 지속적으로 영향을 미치기 때문에, 컨텍스트가 압축되기 전에 미리 신중하게 반영해 놓겠습니다.]

2. 구체적인 의미를 담고 있는 한자어와 자연스러운 통사 구조를 결합하면, 풍부하고 명확한 의미를 전달할 수 있습니다. 따라서 맥락에 적합한 한자어를 적극적으로 활용하고, 그 한자어에 조사와 어미를 붙여서 어휘 사이의 관계를 확실하게 나타내야 합니다. [<쓴 비용을 구하는 토큰 카운트 함수에 문제가 생기면 (상황에 적합한 어휘가 사용되지 않아 의미가 불충분함) /지출 비용 추론 용도의 토큰 카운트 함수의 오류 상황에서 (조사와 어미가 없어 가독성이 낮고 의미 관계가 불분명함)>  → 지출한 비용을 추론하는 토큰 카운트 함수에 오류가 발생하면 (이 지침의 목표 예시)]

3. 일반적인 어휘를 사용해야 하는 자리에 비유적 어휘를 사용하면 가독성이 낮고, 의미가 변질되기 쉽습니다. 따라서 꼭 필요한 경우가 아니라면 비유적 어휘로 일반적인 명사나 동사를 대체하지 않습니다. 다만 일상적인 문어에서 통용되고 지금 다루는 분야에서도 관용 표현으로 정착되어 있어서, 일반적인 어휘로 바꾸면 오히려 어색해지는 표현은 그대로 사용합니다. [<분석의 흐름 → 분석의 방향성>, <코드로 박는 자리 → 코드에 명시하는 상황 (혹은 코드에 명시하는 작업)>, <요청을 받습니다 -> 요청을 확인했습니다 (혹은 요청대로 수행하겠습니다)>]

4. 엠대시(—)는 앞뒤 문장의 관계를 지나치게 함축하기 때문에 자제하고, 문맥과 형식에 따라 콜론이나 접속사로 대체합니다.


### 추가 사항

- 서브에이전트를 호출할 때, 한국어로 프롬프트를 작성했다면 실제로 서브에이전트 호출 도구를 사용하기 전에 이 본문의 지침들이 준수되어 있는지 점검합니다. 서브에이전트가 산출한 결과를 사용자에게 전달할 때에도 본문의 지침들이 그대로 적용됩니다.

im-not-ai 의 분류 ID 를 붙여 두었다. 정본은 그 저장소의 `skills/humanize-korean/references/ai-tell-taxonomy.md` 이다. 빠른 경로용으로 줄인 판은 같은 폴더의 `quick-rules.md` 다. 여기서는 탐지가 아니라 애초에 안 만드는 것이 목적이라 처방을 쓰기 관점으로 적었다.

### 서법 보존(v2.4 부터 필수)

재료가 고른 서법과 강도를 그대로 쓴다. 당위나 요구(「~해야 한다」)를 사실 단정(「~한다」)으로 바꾸지 않는다. 추측이나 유보(「~일 수 있다」, 「~로 보인다」)도 단정으로 올리지 않는다. 문장을 다듬는다는 이유로 주장의 세기를 바꾸면 그것은 의미를 바꾼 것이다. 이 레포의 「숫자를 지어내지 않는다」 규칙과 뿌리가 같다. 시험이 확인하지 않은 동작을 「된다」로 쓰지 않는다.

표지가 되풀이되는 것은 다른 문제다. 같은 「~할 수 있다」가 네 번 이상 이어지면 서법은 둔 채 형태만 바꾼다(A-10, G-1). 두 문단 이상이 「~해야 한다」로 끝나면 당위 문장의 자리만 옮긴다(I-4).

im-not-ai 의 D-13(에세이 결말의 「어쩌면 / 비로소」)은 에세이 한정이라 넣지 않았다. 윤문 전용 장치(변경률 가드, 내용 앵커, 발화 인용 제외)는 쓰기에 필요하지 않아 넣지 않았다.

### S3. 쓸 때 고르지 않는 낱말

im-not-ai v2.4 의 어휘 사전(`skills/humanize-korean/references/lexicon.json` v1.3, 115개)을 옮겼다. 영어(unlock·deliver·lens·layer on)를 옮기다 생긴 말과 분석 보고서에 몰리는 은유다. 문법은 맞지만 한국어 독자는 읽다가 걸린다.

사전은 낱말마다 바꿀 때와 둘 때를 따로 적었다. 같은 낱말도 문맥에 따라 맞는 말이 되기 때문이다(「시스템을 구축하다」, 「카메라 렌즈」). 고정 대체어를 정해 두면 그 말이 새 상투어가 된다. 그래서 아래 「대신」 열은 예시이지 치환표가 아니다. 사전은 장르(보고서, 논문, 일반)마다 문구가 다를 수 있다. 커밋과 PR 과 계획서는 보고서에 가까워서 보고서 문구를 옮겼다.

#### 바꿈 우선(61개)

사전 메인테이너의 블라인드 평가에서 「확실히 어색」을 받은 낱말이다. 「바꿀 때」에 해당하면 한 번도 쓰지 않는다.

| 본질적으로 | 문두 꾸밈말("본질적으로, ~")이거나 강조로만 쓰였을 때, 한 글에서 되풀이될 때 바꾼다. |
| 버팀목·디딤돌(추상) | 한 글에서 두 번 이상 쓰거나 "버팀목이자 디딤돌"처럼 은유를 겹쳐 쓸 때 바꾼다. |
| ~하는 편이 좋다·낫다(권고 말투) | 권고를 한 글에서 두 번 이상 "~하는 편이 좋다/낫다"로 맺을 때 바꾼다. |

## 4. 이 레포의 하우스룰

fluent-korean 과 im-not-ai 가 정하지 않는 것들이다. 대부분 사용자 지적에서 나왔다(2026-06-12 「너무 AI식 말투」, 2026-06-25 「주석에 한자 섞지 마」, 2026-09-23 「그래서 한국어로 해야지?」, 2026-10-27 압축 뒤 영어로 보고했다가 받은 지적). AGENTS.md 와 commit·pr 스킬이 정한 형식은 이 절보다 앞선다.

- 이모지는 쓰지 않는다. 예외는 기계 계약으로 정해진 줄뿐이다. 세션이 받은 PR 본문 끝 표기 줄(`🤖 Generated with [Claude Code](…)`)이 그렇다.
- 불릿은 병렬 항목(발견, 단계, 선택지, 파일 목록)일 때만 쓴다. 항목당 한두 문장이다. 논증과 단일 논점은 산문으로 쓴다.
- 볼드는 불릿이나 문단의 첫 몇 어절에만 건다. 문장 전체를 볼드로 감싸지 않는다. 헤더는 500자 미만 글에는 없고 그 이상에도 셋까지다. pr 스킬의 본문 틀(한 줄 · 왜 · 무엇 · 검사 · 문서)처럼 형식이 정한 헤더는 이 한도에 들지 않는다.
- 엠대시(—), 괄호 부가 설명, 화살표(→)를 산문에 쓰지 않는다. 문장을 끊거나 콜론·접속사로 잇는다. 형식이 정한 기호는 예외다. 커밋 제목과 PR 제목의 ` — `(commit 스킬이 정한 「변경 — 이유」 꼴)와 표 안의 「→」가 그렇다.
- 문장 하나에 생각 하나, 20어절 안팎으로 쓴다. 세미콜론으로 문장을 잇지 않는다. 짧게 쓴다는 것이 토막을 낸다는 뜻은 아니다. 라벨과 콜론보다 서술어가 있는 문장이 낫다.
- 숫자와 측정값을 산문에 늘어놓지 않는다. 독자의 행동을 바꾸는 숫자만 표나 한 줄로 따로 둔다. PR 본문 「검사」 절의 통과 수가 그런 한 줄이다. 숫자는 지어내지 않는다. 모르면 `—` 로 둔다(AGENTS.md).
- 코드 식별자(파일, 함수, 설정 키, 플래그)는 독자가 그리로 가야 할 때만 적는다. 문장당 하나, 문단당 둘까지가 기준이다. 명령, 스니펫, 에러 문구는 코드 블록에 넣는다. 식별자와 영어 낱말 뒤의 조사는 띄어 쓰는 것이 이 레포 관례다(「`local` 을」, 「DB 를」).
- 약어와 내부 용어(M5o, 결정 74, B2, supersede, lanes, drain)는 처음 나올 때 일상어로 풀어 쓴다. 독자가 계획서를 열지 않아도 문장만으로 이해해야 한다. 결정 번호와 절 번호는 풀이 뒤에 근거로 붙인다.
- 문체는 하나로 끝까지 간다. 레포에 남는 글(커밋 본문, 계획서, 리뷰 문서, 코드 주석)은 평어체 「~다」다. 사람에게 직접 건네는 글(PR 본문, 채팅 보고)은 합니다체다. 한 글 안에서 섞지 않는다.
- 한자 표기(前 / 後 / 等 / 時 / 中)는 쓰지 않는다. 앞 / 뒤 / 등 / 때 / 중으로 쓴다. 새로 쓰는 코드 주석도 같다. 기존 주석의 한자는 건드리지 않는다.
- 사용자에게 보이는 글은 작업 중간의 진행 한 줄까지 전부 한국어다. 컨텍스트 압축 뒤에도 같다. 코드, 명령, 식별자, 커밋 제목의 Conventional 접두어(`fix(web):`)는 영어 그대로 둔다. 영어로 쓰기로 정한 문서(README, CHANGELOG, CLI 도움말)는 AGENTS.md 대로 영어다.
- 채팅 보고의 URL 은 장식 없이 한 줄로 쓴다. 굵게, 백틱, 괄호로 감싸면 터미널에서 눌리지 않는다.
- 다음 토큰은 형식 그대로 보존한다. 커밋 제목의 `<type>(<scope>)!:` 접두어와 길이 제한, `Refs: #N` · `Closes #N` · `BREAKING CHANGE:` 트레일러, `Co-Authored-By` 와 세션이 받은 표기 줄, PR 본문 틀의 헤더, 파일:라인, 명령, 해시, 표, 체크박스가 그렇다. 사람이 읽는 설명 문장만 이 스킬의 몫이다.
- 재료에 없는 사실, 수치, 이유를 지어내지 않는다. 모르면 「재료에 없음」이라고 쓴다.

## 5. 직접 쓸 때의 절차

1. 독자와 형식과 문체를 한 줄로 정한다. 누가 읽는지, 어떤 틀인지(commit 스킬의 본문 규칙, pr 스킬의 본문 틀, 계획서 양식), 평어체인지 합니다체인지 정한다.
2. 재료를 목록으로 만든다. diff, 계획서의 절과 결정 번호, 시험 결과, 잡 번호가 재료다. 목록에 없는 것은 쓰지 않는다.
3. 뼈대를 세운다. 결론이나 결과가 먼저이고 근거가 그다음이며 다음 행동이 마지막이다.
4. 초안을 쓴다. 문장마다 주어·목적어·서술어가 있는지, 조사와 어미가 붙어 있는지 본다.
5. §6 으로 점검한다. 걸린 문장만 다시 쓴다. 전체를 다시 쓰면 의미가 샌다.
6. 800자를 넘는 문서(계획서, 리뷰, 핸드오프)는 처음부터 `korean-writer` 에이전트에 재료·독자·형식·출력 경로를 프롬프트로 주고 쓰게 한다. 돌려받은 글은 §6 으로 한 번 더 본 뒤 쓴다. 커밋 본문과 PR 본문은 재료를 다 가진 세션이 직접 써도 된다. 그때도 §6 은 빠뜨리지 않는다.

## 6. 출력 직전 점검

한 항목이라도 걸리면 그 문장만 고친다.

1. 조사와 어미가 빠진 구절이 없는가. 명사만 이어 붙인 구절(「토큰 카운트 함수 오류 상황」)이 없는가.
2. 문장이 서술어와 종결어미로 끝나는가. 헤더와 표와 커밋 제목은 예외다.
3. 비유어(박다, 얹다, 흐름, 자리, 잠식, 신호탄)를 일반어로 바꿀 수 있으면 바꿨는가. S3 의 바꿈 우선 낱말이 0건인가.
4. §3 의 S1 이 0건인가. 연결어미 뒤 쉼표, 「결론적으로」, 이모지, 콜론 헤딩, 경동사(「진행했다」)를 본다.
5. 서법이 재료와 같은가. 「~해야 한다」나 「~일 수 있다」를 단정으로 올린 문장이 없는가.
6. 문장 길이가 다 비슷하지 않은가. 같은 종결어미가 네 문장 연속하지 않는가.
7. 볼드, 불릿, 헤더, 엠대시가 §4 한도 안인가. 커밋 제목과 PR 제목은 `python3 tools/guard_naming.py` 를 통과하는가.
8. 약어를 풀었는가. 재료에 없는 사실이 없는가.
9. 문체가 하나로 일관되는가. 한 대상을 한 이름으로 불렀는가.

## 7. 정밀 윤문이 필요할 때(humanize-korean)

대상은 이미 쓰인 글이다. 남이 준 초안이나 예전 세션이 남긴 문서가 그렇다. 새로 쓰는 글에는 쓰지 않는다.

- 이 머신에는 설치돼 있지 않다(2026-11-19 확인). `~/.claude/skills/humanize-korean` 과 `~/Documents/GitHub/im-not-ai` 가 모두 없다.
- 전역 설치는 사용자 설정을 바꾸는 일이라 오너가 요청할 때만 한다. 방법은 둘이다. 세션에서 `/plugin marketplace add epoko77-ai/im-not-ai` 를 실행한 뒤 `/plugin install humanize-korean@im-not-ai` 를 실행한다. 아니면 저장소를 클론한 뒤 `./install.sh --claude-only` 를 실행한다(기본은 심링크 설치). `--copy` 는 저장소를 지워도 남는 복사 설치이고 v2.4.7 에서는 런타임 스크립트도 함께 복사한다. 커밋 전용 `commit-ko` 는 `--extras` 를 줘야 깔린다. 설치 스크립트는 `CLAUDE_HOME`(기본 `~/.claude`)에 까니 세션 설정 폴더가 다르면 그 값을 맞춘다.
- 산출물은 실행한 폴더의 `_workspace/<run_id>/` 에 쌓인다. 이 레포의 `.gitignore` 에는 `_workspace/` 가 없다. 레포 안에서 돌리지 말고 세션의 scratchpad 같은 레포 밖 폴더에서 돌린다.
- 설치돼 있지 않은데 정밀 윤문을 지시받았으면 건너뛰되 산출물 보고에 「정밀 윤문 생략(im-not-ai 미설치)」을 적는다. 조용히 건너뛰면 아무도 모른다.

## 8. 갱신

- fluent-korean: `git clone --depth 1 https://github.com/snflkd/fluent-korean` 한 뒤 `plugins/fluent-korean/output-styles/fluent-korean.md` 본문(프런트매터 제외, `##` 을 `###` 으로 한 단계 내림)을 §2 에 통째로 다시 붙인다. 기준 커밋은 출처 표에 적는다. 출력 스타일로도 쓰려면 같은 파일을 `~/.claude/output-styles/` 에 두고 설정의 `outputStyle` 을 바꾼다. 사용자 전역 설정이라 오너가 정한다.
- im-not-ai: 저장소를 받지 않아도 읽을 수 있다. `gh api "repos/epoko77-ai/im-not-ai/contents/<경로>?ref=<커밋>" -H 'Accept: application/vnd.github.raw'` 로 아래 세 파일을 본다. 발행 노트는 `gh release list -R epoko77-ai/im-not-ai` 로 찾는다.
  - `skills/humanize-korean/references/quick-rules.md` 에서 §3 의 ID 와 처방이 바뀌었는지 본다.
  - `skills/humanize-korean/references/ai-tell-taxonomy.md` 에서 빠른 경로에서 빠진 항목(A-16, A-17, A-23, C-1, D-4, F-1, F-2, G-3, H-1, H-3, I-1)의 처방을 본다.
  - `skills/humanize-korean/references/lexicon.json` 으로 S3 를 다시 만든다. 표는 손으로 옮기지 않는다. 아래 명령이 찍는 행을 글자 그대로 붙인다.

    ```sh
    python3 - lexicon.json <<'EOF'
    import json, sys
    g = "보고서"
    for e in json.load(open(sys.argv[1]))["entries"]:
        cells = [e["headword"], e["change_when"][g]]
        if e["tier"] == "change":
            cells += [e["how"][g], e["keep_when"][g]]
        print(e["tier"], "| " + " | ".join(c.replace("|", "\\|") for c in cells) + " |")
    EOF
    ```
- 이 스킬과 `korean-writer` 의 원본은 dolomood-renew 레포(`dolomood-app-renew/.claude/skills/korean-writing/`)에 있다. 이 레포 판은 원본(im-not-ai v2.3.2 기준 판)에서 갱신한 §3·S3·§9 와 별도로 이 레포에 맞게 고친 곳이 있다. 앞머리와 출처 표, §1, §3 의 C-5 · B-1 · 동의어 돌려쓰기 행, §4, §5 의 1·2·6항, §6 의 2·3·5·7·9항, §7 이다. §2·§3 을 갱신하면 두 레포를 같이 맞춘다.
- 들이지 않은 것도 적어 둔다. k-skill 의 PERSONALITY 절(1인칭 의견, 곁가지, 흐트러짐을 허용하라는 조언)은 §4 와 부딪혀 넣지 않았다. k-skill 의 글자 수 맞추기도 쓰기 규칙이 아니라서 넣지 않았다.
