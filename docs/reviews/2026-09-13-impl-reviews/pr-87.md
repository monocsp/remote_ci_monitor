대부분 핵심 설계와 일치하지만, 결정 73·74의 오류 경로가 완결되지 않았습니다.

- 결정 73의 정상 경로는 맞습니다. 원본을 `mode=ro`로 열고 SQLite online backup을 만든 뒤, 사본에 `Store` 마이그레이션과 `Janitor.plan()`을 적용합니다. [store.py:341](src/remote_ci_monitor/store.py:341), [cli.py:747](src/remote_ci_monitor/cli.py:747)
- WAL에만 있는 변경도 사본에 포함하며, 원본 마이그레이션 회귀를 mutcheck로 잠갔습니다. [test_offline_gc.py:120](tests/test_offline_gc.py:120), [mutcheck.py:256](scripts/mutcheck.py:256)
- 결정 74의 정상 경로도 맞습니다. `_conn()`이 `journal_mode=WAL`을 설정하기 전에 백업하며, `integrity_check`와 버전 검증 뒤 `os.replace()`합니다. [store.py:627](src/remote_ci_monitor/store.py:627), [store.py:669](src/remote_ci_monitor/store.py:669)
- 결정 78의 v16 SQL은 명세 그대로입니다. 대장 없는 실패·타임아웃 라벨만 `last_step`으로 옮기고, 취소·유실은 두 라벨을 비웁니다. [store.py:319](src/remote_ci_monitor/store.py:319)
- 어긋남: “어느 단계든 불완전하면 exit 3”이 실제 마이그레이션 예외와 임시 사본 생성·정리 실패에는 적용되지 않습니다. [cli.py:764](src/remote_ci_monitor/cli.py:764), [cli.py:780](src/remote_ci_monitor/cli.py:780), [cli.py:814](src/remote_ci_monitor/cli.py:814)
- 어긋남: “백업 정리 실패는 경고”라고 했지만 백업 디렉터리 열거 실패는 조용히 무시합니다. [store.py:687](src/remote_ci_monitor/store.py:687)

## B. 고쳐야 할 구현 문제

- P1 — 사본 마이그레이션의 실제 SQLite 오류가 exit 3으로 변환되지 않습니다. `Store(copy)`에서 잡는 것은 `StoreError`뿐이지만, `_MIGRATIONS`의 SQL 실패는 `sqlite3.OperationalError`·`IntegrityError` 등이 그대로 올라옵니다. `main()`도 이를 잡지 않아 traceback과 통상 exit 1이 됩니다. 재현 조건은 사본 생성·자동 백업은 성공하지만 migration SQL이 실패하는 DB, 예를 들어 불일치한 구형 스키마나 마이그레이션 쓰기 도중의 I/O 오류입니다. 업그레이드 전에 바로 이 실패를 감지하는 것이 기능의 목적이므로 P1입니다. [cli.py:779](src/remote_ci_monitor/cli.py:779), [store.py:652](src/remote_ci_monitor/store.py:652), [cli.py:1963](src/remote_ci_monitor/cli.py:1963)

- P1 — 임시 DB 삭제 실패를 무시하고 성공을 출력합니다. `shutil.rmtree(..., ignore_errors=True)`가 실패하면 운영 DB 전체 사본과 사본의 WAL·백업이 `$TMPDIR/rcm-gc-dryrun-*`에 남지만 exit 0입니다. 재현 조건은 정리 시점의 권한 변경, 파일시스템 I/O 오류 또는 삭제를 막는 외부 상태입니다. 0700 디렉터리라 타 사용자 노출은 제한되지만, 데이터 잔류와 “사본을 지웠다”는 거짓 성공이 생깁니다. [cli.py:814](src/remote_ci_monitor/cli.py:814)

- P1 — newer-schema 거절 메시지가 존재하지 않는 백업을 복원하라고 할 수 있습니다. 경로를 “DB가 실제로 마이그레이션되기 전 버전”이 아니라 현재 실행 중인 옛 빌드의 `DB_VERSION`으로 계산합니다. 예를 들어 v15 DB를 향후 v21 빌드로 바로 올리면 생성되는 자동 백업은 `v15.bak` 하나인데, v16 빌드는 `v16.bak`을 복원하라고 안내합니다. 현재 테스트도 백업 파일을 만들지 않고 문자열만 단언해 이 문제를 통과시킵니다. [store.py:419](src/remote_ci_monitor/store.py:419), [test_store_m5i.py:154](tests/test_store_m5i.py:154)

- P2 — 오래된 백업 정리에서 디렉터리 열거 실패가 경고 없이 사라집니다. `backup/`에 쓰기·실행 권한은 있지만 읽기 권한은 없는 경우처럼 새 백업 생성은 가능하고 `iterdir()`만 실패하면 재현됩니다. 결정 74가 약속한 경고가 없고 백업이 계속 쌓입니다. [store.py:692](src/remote_ci_monitor/store.py:692)

- P2 — 이번 요청의 “오류·상태·로그에 경로 금지”와 충돌합니다. 오프라인 JSON의 `offline.database`, 성공 stdout, no-database·schema 오류, migration backup 오류가 절대경로를 냅니다. 실제 unlink 경고의 `OSError`도 전체 경로를 포함할 수 있습니다. 특히 JSON의 DB 경로는 명세가 요구한 “스키마 버전과 사본 여부”에 필요하지 않습니다. 단, 구형 빌드 거절 메시지에 복원 경로를 넣으라는 세부 명세와는 서로 충돌하므로 그 부분의 최종 정책은 확인 못 함입니다. [cli.py:750](src/remote_ci_monitor/cli.py:750), [cli.py:805](src/remote_ci_monitor/cli.py:805), [cli.py:820](src/remote_ci_monitor/cli.py:820), [store.py:682](src/remote_ci_monitor/store.py:682)

P0는 찾지 못했습니다. 원본 DB를 사본 대신 마이그레이션하던 본래 사고는 정상 경로와 테스트 양쪽에서 막혔습니다.

## C. 테스트가 잠그지 못한 것

- migration 실패 테스트가 현실의 `sqlite3.Error`가 아니라 `StoreError`를 직접 던집니다. 따라서 위 P1을 놓쳤습니다. [test_offline_gc.py:198](tests/test_offline_gc.py:198)
- deadline 테스트는 `--timeout 0`으로 첫 페이지 전에만 실패시킵니다. progress callback이나 페이지별 deadline 검사를 제거해도 이 테스트는 통과합니다. 중간 복사 중 시간이 만료되는 테스트와 해당 mutcheck가 필요합니다. [test_offline_gc.py:188](tests/test_offline_gc.py:188), [store.py:375](src/remote_ci_monitor/store.py:375)
- `mkdtemp()` 실패, `rmtree()` 실패, `Store.close()` 실패를 모두 검사하지 않습니다. 특히 정리 실패 시 exit 3과 사본 잔류 보고가 잠기지 않았습니다.
- 백업 정리 시험은 개별 `unlink()` 실패만 보고 `iterdir()` 실패를 보지 않습니다. [test_store_m5i.py:109](tests/test_store_m5i.py:109)
- newer-schema 시험은 안내된 `.bak`의 존재를 확인하지 않습니다. 오히려 백업이 하나도 없는 상태에서 가공된 경로를 정답으로 잠급니다. [test_store_m5i.py:154](tests/test_store_m5i.py:154)
- 경로 비노출 단언이 없으며, no-database 시험은 반대로 절대경로 노출을 요구합니다. [test_offline_gc.py:175](tests/test_offline_gc.py:175)
- mutcheck 설명 주석의 번호가 실제 목록과 어긋납니다. 새 변이는 ㉔·㉕인데 구현부 주석은 ㉓·㉔입니다. [mutcheck.py:254](scripts/mutcheck.py:254)

## D. 문서·CHANGELOG 불일치

- CHANGELOG의 “어느 단계든 불완전하면 exit 3”과 “사본을 삭제한다”는 위의 migration·정리 오류 경로에서는 사실이 아닙니다. [CHANGELOG.md:192](CHANGELOG.md:192)
- CHANGELOG의 “메시지가 그 백업을 지목한다”와 운영 문서의 고정 `v<old>.bak` 복원 예시는 버전을 건너뛴 업그레이드에서 존재하지 않는 파일을 가리킬 수 있습니다. [CHANGELOG.md:201](CHANGELOG.md:201), [operating.md:122](docs/operating.md:122)
- 운영 문서는 사본을 만들거나 마이그레이션하지 못하면 항상 exit 3이라고 하지만 raw SQLite migration 오류에는 traceback/exit 1입니다. [operating.md:88](docs/operating.md:88)
- 복원 후 `jobs/<id>/` 로그와 `workspaces/<id>/`를 모두 sweeper가 orphan으로 세는 것처럼 적었지만, 인벤토리는 workspace와 `tree.tar.gz`만 셉니다. 로그만 남은 `jobs/<id>/`는 세지 않습니다. [operating.md:131](docs/operating.md:131), [janitor.py:423](src/remote_ci_monitor/janitor.py:423)
- 정본 `PLAN.md` 결정 80은 `백업 → 정지`인데 운영 문서는 `정지 → 백업`입니다. 다만 상세 명세 §6과 결정표는 문서 쪽 순서를 지지하므로 기능상 어느 쪽이 최종 정본인지는 확인 못 함입니다. [PLAN.md:679](PLAN.md:679), [operating.md:96](docs/operating.md:96)
