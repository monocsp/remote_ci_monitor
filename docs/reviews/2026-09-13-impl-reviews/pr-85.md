## B. 버그 · 경쟁 · 자원 · fail-open · 보안 · 호환

P0 없음. P1 하나. P2 셋.

- **B-1 P1 — 버전을 안 올린 main push 는 전부 빨간 run 이 된다.** `tag-release.yml` 「태그가 이미 있으면」 단계(diff L34-47): 태그가 있고 `AT != GITHUB_SHA` 면 `::error::… bump __version__ instead of reusing it` + `exit 1`. 그런데 첫 릴리스 뒤에 오는 **모든** 비-범프 main push — 문서만 고친 dev→main PR, 릴리스 뒤 후속 머지 — 는 정확히 이 조건이다(태그는 옛 릴리스 커밋에, `GITHUB_SHA` 는 새 머지 커밋). 룰셋 필수 체크는 `test`·`main-from-dev-only` 뿐이라 머지가 막히진 않지만, 매번 실패 메일이 오고 메시지는 「버전을 올려라」는 틀린 조언이다. 명세 §3 표 7 「같은 버전 재푸시는 무동작」과 CONTRIBUTING 「A merge that does not bump `__version__` is a no-op」(diff L79-80)이 둘 다 이 구현과 어긋난다. 재현: 태그 `vX` 가 있는 상태에서 `__version__` 그대로인 커밋을 main 에 push. 고치는 길: 「태그 커밋이 `GITHUB_SHA` 의 조상이면(`git merge-base --is-ancestor "$AT" "$GITHUB_SHA"`, fetch-depth 필요) 무동작, 조상이 아니면 재사용 거절」 — 그러면 진짜 재사용(옛 버전 번호로 되돌린 커밋)만 거절한다.
- **B-2 P2 — 릴리스가 태그 생성 뒤에 실패하면 문서의 재실행 길이 막혀 있다.** `tag` 잡이 태그를 민 뒤 `release`(build/smoke/github-release)가 깨지면 태그는 이미 origin 에 있다. CONTRIBUTING 「To re-run a release by hand, push the tag yourself: `git tag v0.1.0 <main-sha> && git push origin v0.1.0`」(diff L81-82)는 이때 `Everything up-to-date` 로 아무것도 깨우지 않는다. 실제 길은 ① Actions 에서 그 `Tag release` run 을 Re-run(불린 잡이 다시 돈다), ② 태그를 지우고 다시 밀기(`git push origin :refs/tags/vX` 뒤 손 push — `on: push: tags` 로 `release.yml` 이 돈다). 다음 push 는 B-1 로 `AT = GITHUB_SHA` 라 무동작이니 자동 경로로는 다시 못 돈다. 문서 한 줄이 필요하다.
- **B-3 P2 — 권한·비밀 폭이 필요보다 넓다(경계는 안 깨진다).** (a) `tag-release.yml` 은 `permissions: contents: write` 를 **워크플로 수준**에 둔다(`tag` 잡만 필요). 테스트 `test_tag_release_declares_contents_write_at_workflow_level` 이 그 모양을 잠가 두었으니 의도된 선택이지만 잡 수준이 최소 권한이다. (b) `secrets: inherit` 는 레포 비밀 전부를 `release.yml` 에 넘기는데 그 워크플로는 비밀을 하나도 안 쓴다(PyPI 는 trusted publishing, `GH_TOKEN` 은 `github.token`). 없애도 된다. 호출된 잡의 권한이 호출 잡의 `contents: write · id-token: write` 로 덮이는 것은 테스트 `test_tag_release_caller_permissions_cover_every_called_job` 이 잡 단위로 잠갔다 — 좋다.
- **B-4 P2 — 불려 온 `smoke` 잡은 태그가 아니라 호출자의 `GITHUB_SHA` 를 받는다.** `release.yml` `smoke` 잡(87-97행)의 `actions/checkout@v4` 에 `ref` 가 없다. 자동 경로에선 태그를 방금 `GITHUB_SHA` 에 만들었으니 같은 커밋이고, 손 태그 경로에선 기본 ref 가 태그라 문제없다. 다만 `build`·`github-release` 만 `ref: refs/tags/…` 로 고정하고 `smoke` 는 빠뜨린 것이라 일관성 문제 — `scripts/smoke_install.sh` 가 태그 커밋과 다른 것을 검사할 길은 지금 없다(「확인 못 함」— 같은 run 안에서 main 이 움직여도 `GITHUB_SHA` 는 고정이므로 실제 어긋남은 없다고 본다).

문제 없다고 본 것.
- 경쟁: main 에 두 push 가 잇달아 오면 뒤 run 이 B-1 로 실패할 뿐 태그가 엉키진 않는다(`git push` 는 원자적, 이미 있으면 거부).
- 태그 존재 확인의 `ls-remote` 관용구는 실측대로 맞다(위). `cut -f1` 은 탭 구분이라 안전.
- `actions/checkout@v4` 기본 `persist-credentials: true` 라 `git push` 가 `GITHUB_TOKEN` 을 쓴다 · `git config user.*` 를 먼저 둔다 · `git tag -a … "$GITHUB_SHA"` 는 fetch-depth 1 로도 된다(HEAD 가 그 커밋).
- `release.yml` 의 `github.ref_name` 은 전부 `inputs.tag || github.ref_name` 로 감싸였고(테스트가 bare 사용 부재를 잠금) checkout 도 `refs/tags/${{ env.TAG }}` — 불려 왔을 때 `github.ref_name == main` 인 함정을 제대로 피했다. `vars.PYPI_PUBLISH` 는 불려 온 워크플로에서도 읽힌다.
- 노출: 로그에 sha·태그 이름뿐. 비밀 없음. 호환: 손 태그 경로(`on: push: tags`) 유지 → 옛 절차도 그대로 돈다.

## C. 테스트가 잠그지 못한 것

- **C-1 — B-1 의 의미론이 안 잠겨 있다.** `test_tag_release_is_idempotent_and_refuses_a_reused_version` 은 `exit 0` 과 `exit 1` 이 **어딘가** 있고 `"$GITHUB_SHA"` 와 비교한다는 것만 본다. 「같은 커밋 → 0」「다른 커밋 → 1」의 분기도, 「조상 → 무동작」이 되어야 한다는 것도 잠기지 않는다. B-1 을 고쳐도 이 테스트는 그대로 초록이라 재발 방지가 없다 — 최소한 `merge-base --is-ancestor` 문구를 요구하든지, `run` 블록을 가짜 `git` 로 실제 실행해 보는 시험이 필요하다.
- **C-2 — 문면 검사의 한계.** 전부 정규식 + `bash -n`. `run: |` 안의 `python - <<'PY'` 히어독은 bash 문법만 통과하면 파이썬 오류가 있어도 초록이다(pre-existing, `release.yml` 도 같음). `${{` 가 스크립트 본문에 없다는 단언은 좋다.
- **C-3 — `smoke` 잡의 checkout ref(B-4)는 `test_release_checks_out_the_tag_it_was_given` 이 `build`·`github-release` 만 돈다.** 일관성을 원하면 세 잡 모두.
- **C-4 — 실전 검증 없음.** 위 「확인 못 함」— 머지 시점에 돌려 볼 수 없는 종류의 변경이니 흠은 아니지만, v0.2.6 머지 때 첫 run 을 **지켜보고** 결과(태그·Release·노트 본문)를 M5i 보고에 적어야 한다. `docs/acceptance/reports/` 에 I8-2 실행 기록은 없다(「확인 못 함」— `2026-09-10-m5i-verify-client.md` 가 I8-2 를 언급하나 본문은 안 읽었다).
- 잘 잠근 것: 호출 잡 권한이 호출된 모든 잡의 권한을 덮는지(잡 단위 순회) · `workflow_call.inputs.tag` 에 default 없음 · `github.ref_name` bare 사용 부재 · 브랜치 push 부재 · CONTRIBUTING 3단계에서 손 태그 제거.

## D. 문서 · CHANGELOG

- **D-1 P1(= B-1 의 문서 면)** — CONTRIBUTING 「A merge that does not bump `__version__` is a no-op」은 구현과 다르다(위). 문장을 구현에 맞추든지(권장하지 않음) 구현을 문장에 맞추든지.
- **D-2 P2(= B-2)** — 「To re-run a release by hand, push the tag yourself」는 태그가 이미 있는 자동 경로 실패에는 안 통한다. Re-run 버튼 또는 태그 삭제 후 재푸시를 적는다.
- **D-3 P2 — CHANGELOG 에 #85 항목이 없다.** `[0.2.6]`·`[Unreleased]` 어디에도 `tag-release`/`#85` 가 없다(grep). 사용자에게 보이지 않는 CI 변경이라 뺀 것일 수 있으나, 이 프로젝트는 0.2.0 절에 「release workflow (GitHub Release + optional PyPI)」를 적은 전례가 있고(CHANGELOG 615행), 「릴리스가 어떻게 만들어지는가」는 배포자에게 보이는 변화다. 한 줄이면 된다(「확인 못 함」— 오너가 CI 변경을 CHANGELOG 밖에 두기로 한 규칙이 있는지).
- 맞는 것: PLAN.md 결정 82(681행)가 있고 `(M5i I8, #85)` 링크까지 있다 · `docs/operating.md`·README 에는 손 태그 절차가 없어 옮길 것이 없다 · `release.yml` 머리 주석이 두 입구와 `TAG` 결정 규칙을 정확히 설명한다.
