구현의 큰 뼈대(v17, 해시 저장, 기본 off, strict 모드, health/status 추가)는 명세와 맞지만, 핵심인 “제출 참여자별 권한”이 CLI 상태 파일과 leave 처리에서 깨집니다. P0는 없고, P1 3건 때문에 그대로 머지하면 안 됩니다. 코드는 변경하지 않았습니다.

## A. 명세·결정 87 정합성

맞는 부분:

- v17 `submissions` 표, SHA-256만 저장, 메타데이터와 같은 트랜잭션에서 삭제
- 매 `POST /jobs` 응답에 별도 capability 발급
- 기본값 off와 0.2.x 기존 취소 규칙 유지
- strict 모드에서 capability 또는 admin만 허용, `--force` 없음
- health/status 키 추가, schema v1 유지
- v16 경계 백업

어긋나는 부분:

1. **같은 bearer token의 제출들을 CLI가 구별하지 못합니다.**  
   [submissions.py:78](.codex-review/110.diff:983)에서 같은 서버·잡·지문·역할의 이전 항목을 지우고, [submissions.py:131](.codex-review/110.diff:1036)에서 같은 지문이면 `cancel_job`을 우선합니다. 따라서 같은 토큰의 두 번째 세션이 합류한 뒤 `rcm cancel N`을 실행하면 자기 `leave_submission`이 아니라 첫 세션의 `cancel_job`을 보내 잡 전체를 취소합니다. 결정 87의 핵심과 반대입니다.

2. **`leave_submission`이 그 capability의 참여자가 아니라 요청에 사용한 bearer 이름을 제거합니다.**  
   [server.py:1805](.codex-review/110.diff:700)–1815. `submissions` 행에는 참여자 이름이 없고, `remove_joiner(job_id, token.name)`을 호출합니다. “그 제출 참여자만 제거”를 표현하지 못합니다.

3. **독립 실행한 `rcm wait --job N`의 Ctrl-C 계약이 유지되지 않습니다.**  
   `cli.py:770-772`는 항상 `joined=False`, capability 없이 `_wait()`를 부릅니다. 합류자가 `run --no-wait` 후 `rcm wait`로 이어서 기다리다 Ctrl-C해도 participation을 제거하지 않습니다. 명세 §G5 119–130 및 PLAN의 `rcm wait` 계약과 불일치합니다.

4. **웹 admin 예외가 완성되지 않았습니다.**  
   strict 모드 잠금 자체는 admin에게 열리지만, 기존 `mine` 조건이 그대로라 admin도 남의 잡을 취소할 수 없습니다. [app.js:1497](.codex-review/110.diff:1138), [app.js:1594](.codex-review/110.diff:1148). 명세의 “admin 토큰이 아닌 한 비활성” 및 API의 admin 범위와 다릅니다.

5. G5.23의 문자열 `"yes"`/`"1"` 허용은 검증 보고서가 수용 시나리오 편차라고 자인합니다([보고서 diff:116](.codex-review/110.diff:116)). 다만 원본 `docs/acceptance/m5j-verification-scenarios.md`가 제공되지 않아 해당 시나리오의 정확한 요구는 **확인 못 함**입니다.

## B. 고쳐야 할 구현 문제

- **P1 — 같은 토큰의 다른 세션이 잡 전체를 취소할 수 있음**  
  위치: `submissions.py:78-86, 116-138`, `cli.py:780-791`.  
  재현: strict=true, 같은 `XDG_STATE_HOME`과 bearer token으로 세션 A가 새 잡 제출 → 세션 B가 같은 잡에 합류 → B에서 `rcm cancel N`. 조회가 A의 `cancel_job`을 우선해 잡 전체가 취소됩니다. 테스트도 이 잘못된 선택을 기대값으로 고정합니다(`tests/test_cancel_capability.py:634-644`).

- **P1 — leave capability의 대상 혼동과 동시 재사용 경쟁**  
  위치: `server.py:1805-1815`, `store.py:1739-1744`.  
  재현: Bob과 Charlie가 합류한 잡에서 Bob의 leave secret을 Charlie bearer로 보내면 Bob의 capability 행을 지우면서 Charlie의 `joiners` 행을 지웁니다. 또한 capability 조회·삭제·joiner 삭제가 한 트랜잭션이 아니므로 같은 leave secret을 동시에 두 요청이 조회하면 둘 다 통과해 두 참여자를 제거할 수 있습니다. `remove_submission()` 결과도 확인하지 않습니다.

- **P1 — 로컬 capability 파일의 다중 프로세스 쓰기가 안전하지 않음**  
  위치: [submissions.py:78-113](.codex-review/110.diff:983).  
  재현: 같은 Unix 사용자에서 `rcm run` 두 개를 동시에 실행. 둘이 동일 파일을 읽고 동일한 `submissions.json.tmp`를 `O_TRUNC`로 열어 덮어쓰므로 JSON 손상, 한쪽 `os.replace` 실패, 또는 마지막 쓰기가 다른 항목을 잃는 문제가 생깁니다. strict 모드에서는 잃은 잡을 비-admin이 취소할 수 없습니다.

- **P2 — 잡/합류와 capability 생성이 원자적이지 않음**  
  위치: [server.py:1318-1353](.codex-review/110.diff:634), `server.py:1660-1705`.  
  `join_or_bump()` 또는 `create_job()`이 먼저 커밋된 뒤 `add_submission()`합니다. DB full·ID 충돌·I/O 오류가 나면 HTTP는 실패하지만 잡이나 합류·join_count는 남고 capability는 없습니다. 특히 `git_ref` 잡은 실행될 수도 있습니다.

- **P2 — 저장 실패나 200개 초과 시 활성 잡의 유일한 취소 권한을 잃음**  
  위치: `cli.py:237-265`, [submissions.py:31-32, 98](.codex-review/110.diff:936).  
  일반 `rcm run`은 저장 실패 시 secret을 출력하지 않으면서 진행하고, 임의 상한 200개는 활성 여부와 무관하게 옛 항목을 삭제합니다. strict 모드에서는 admin 없이는 긴 잡을 멈출 방법이 사라집니다.

- **P2 — 알 수 없는 DB role이 `cancel_job`으로 승격되는 fail-open**  
  위치: `server.py:1808-1816`.  
  조건은 `role == leave_submission`만 확인하고 나머지는 전부 `_cancel_job()`으로 보냅니다. DB 손상·수동 복구·미래 role 값이 잡 취소 권한이 됩니다.

- **P2 — 로컬 오류 출력에 절대 경로 노출**  
  위치: [cli.py:260-264](.codex-review/110.diff:379), [cli.py:785-789](.codex-review/110.diff:523).  
  상태 저장 실패 또는 항목 없음만으로 사용자 홈을 포함한 `state_path()`가 stderr에 찍힙니다. 요청의 “상태·오류·로그에 경로 금지”와 맞지 않습니다.

- **P2 — 현재 PR 버전에서 옛 클라이언트의 `rcm check`가 거짓 OK**  
  위치: `__init__.py:7`, `cli.py:380-390`, `server.py:1990-1994`.  
  서버와 옛 클라이언트가 둘 다 0.2.6이면 `_client_row()`가 `min_client_version=0.2.7`을 보기 전에 “same as server”로 OK를 냅니다. strict 모드 취소는 실제로 403입니다. 0.2.7 버전 상승 후에는 사라지지만 이 PR HEAD의 진단은 fail-open입니다.

## C. 테스트가 잠그지 못한 것

- `tests/test_cancel_capability.py:634-644`는 같은 토큰의 합류자보다 요청자 capability가 이긴다는 잘못된 동작을 오히려 고정합니다.
- `tests/test_cancel_capability.py:598-656`의 “atomically” 테스트는 순차 쓰기뿐이며 다중 프로세스·고정 `.tmp` 경쟁을 검사하지 않습니다.
- leave capability를 다른 bearer로 보내는 경우와 같은 secret의 동시 재사용이 없습니다.
- `add_submission()` 실패 시 잡 생성·합류·join_count가 롤백되는지 없습니다.
- 독립 `rcm wait --job`에서 저장된 leave capability를 사용하는 Ctrl-C 테스트가 없습니다.
- 웹 테스트는 `cancelLocked()` 순수 함수만 보고, admin이 남의 행에서 실제 버튼을 쓸 수 있는지 검사하지 않습니다.
- 옛 0.2.6 클라이언트와 현재 0.2.6 strict 서버의 실제 `rcm check` 결과를 자동 테스트하지 않습니다.
- mutcheck는 strict 분기 전체 제거 하나뿐이라 role 반전, 지문 폴백, capability 소비 원자성은 잡지 못합니다.
