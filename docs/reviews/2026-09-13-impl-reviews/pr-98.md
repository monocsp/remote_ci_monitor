## A. 의도와 구현

의도(주석 156~158행): 「첫 응답까지의 마감은 넉넉하게 … `CDP: no reply before the deadline` 로 하루 네 번 빨갰다」. 구현: `_attach_first_page(timeout=COLD_START_SECONDS)`, `Page.enable`·`Page.addScriptToEvaluateOnNewDocument` 에 `timeout=COLD_START_SECONDS`.

**그런데 「첫 응답」을 기다리는 호출은 바뀌지 않았다.** `_attach_first_page()`(`tests/test_web_browser.py:211-221`) 안의 두 호출 —

```python
targets = self.call("Target.getTargets")["targetInfos"]        # :214 — timeout 인자 없음 → 기본 15.0
…
return self.call("Target.attachToTarget", params)["sessionId"] # :221 — 마찬가지
```

— 은 `call()` 의 기본 `timeout=15.0`(`:194`) 그대로다. `_attach_first_page` 의 `timeout` 인자는 **「페이지 타깃이 생길 때까지 되묻는 루프」의 마감**(`:212 deadline`, 실패 문구 「Chrome never created a page target」)이지 개별 CDP 응답의 마감이 아니다. Chrome 이 찬 기동 중이라 첫 `Target.getTargets` 응답이 15초를 넘기면 `_read_msg`(`:178-181`) 가 예전 그대로 「no reply before the deadline」을 던진다. 60초를 받은 `Page.enable`·`addScript` 는 이미 붙은 뒤의 호출이라 찬 기동과 무관하다.

   셋 다 `FAILED tests/test_web_browser.py::test_desktop_dom_shows_running_and_queued_jobs - AssertionError: CDP: no reply before the deadline`, 트레이스백 `tests/test_web_browser.py:421 → :160 in __init__ → :214 in _attach_first_page → :205 in call`. **:214 가 바로 `Target.getTargets`** 다. `test_desktop_dom_…` 은 모듈의 첫 Chrome 테스트(`:420`)라 찬 기동을 맞는 자리다. #98 이전의 실패(run 34451306115, #95, 07:42Z)와 프레임이 같다. 즉 #98 은 원인 호출을 비켜 갔고, #82 가 ubuntu 에서 Chrome 을 필수로 만든 탓에 이 플레이크는 모든 PR 의 필수 체크 `test` 를 빨갛게 만든다(그 세 run 모두 `test` 잡도 failure). 고치는 법: `_attach_first_page` 안에서 `self.call("Target.getTargets", timeout=…)`·`attachToTarget` 에도 남은 시간을 넘긴다(`max(1.0, deadline - time.monotonic())` 이 자연스럽다). 3.11 에서도 났으니 주석의 「3.13」 한정도 지운다.
2. **P2 — 주석이 구현을 잘못 말한다.** `:156-158` 「첫 응답까지의 마감은 넉넉하게」 — 위와 같이 사실이 아니다. 고칠 때 같이.
3. **문제 없음 —** 붙은 뒤의 `Page.enable`·`addScript` 60초는 init 안에서만 쓰이고 `open()`·`eval()` 은 15초 그대로라 「늘어진 페이지를 숨기지 않는다」는 약속은 지켜진다.

## C. 테스트가 잠그지 못한 것

- CI 러너의 찬 기동을 단위 테스트로 잠그기는 어렵다. 대신 값싼 잠금: `Chrome.__init__` 이 부르는 **모든** `call` 이 `COLD_START_SECONDS` 를 받도록 `_attach_first_page` 가 `call` 을 한 번 감싼 헬퍼(`self._call_cold(...)`)로만 부르게 하면 누락이 구조적으로 사라진다. 또는 `Chrome.call` 을 가짜 파이프로 20초 지연시켜 init 이 살아남는지 보는 테스트(무겁다 — 지적만).
- 관련 메모: 「Flaky e2e worker restart test」는 다른 테스트(`test_server_restart_keeps_the_remote_job_running…`)라 이 건과 무관.
