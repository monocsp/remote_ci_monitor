## B. 버그 · 경쟁 · 자원 · fail-open · 보안 · 호환

P0 없음. P1 없음(문서 쪽 P1 은 D-1). P2 셋.

- **B-1 P2 — 마커 조회의 예외 폭이 형제 경로보다 좁아 문서 전체가 500 이 된다.** `server.py` `_with_step_timeline()` (diff L310-315) 는 `sqlite3.Error` 만 잡는다. 그런데 `Store.markers()` (`store.py:2003-2011`) 는 행마다 `json.loads(e["payload"])` · `p["kind"]` · `p["value"]` · `_dt(e["at"])` 를 한다 — `ValueError`/`KeyError`/`TypeError` 는 통과해 `Handler` 의 총괄 핸들러(`server.py:2059`)로 가고 `GET /jobs/<id>` 가 **500 `internal error`** 가 된다. 그러면 `state`·`failures`·`artifacts` 까지 그 잡의 문서 전체가 사라지고 `rcm wait --job N` 은 3 으로 끝난다. 같은 자료를 읽는 `/api/status` 쪽(`server.py:910-911` `markers_for` → `except Exception`)과 `job_storage`/`artifact_storage`(`:745`, `:773`)는 `Exception` 을 잡고 `_error_code` 로 내려앉는다(`_error_code` 는 이미 sqlite 아닌 예외를 `internal_error` 로 매핑한다, `:1957`). fail-open 은 아니다(닫힌다) — 그러나 「부가 정보 하나 때문에 정본 문서가 죽는」 반경이 형제 경로와 다르다. 재현: 종료 잡 N 의 `events` 행 하나를 `UPDATE events SET payload='x' WHERE job_id=N AND kind='marker'` 로 깨고 `GET /jobs/N`. 현실성: 페이로드는 서버 자신이 쓰므로 운영에서 날 조건은 「확인 못 함」. 고치려면 `except Exception as e:  # noqa: BLE001` + 같은 `_error_code(e)`.
- **B-2 P2 — `finished_at` 이 없는 종료 잡 폴백은 매 요청마다 값이 달라지는 타임라인을 낸다.** diff L316-318 `now=job.finished_at or self.now_fn()`. 이 가지로 오면 `progress_from_markers` 는 마지막 스텝을 닫지 않아(`finished_at is None` → `current`) `ended_at: null` · `seconds` 가 지금 시각 기준으로 요청마다 커진다 — 문서(`configuration.md` 「the same values the queue showed … kept after it finished」)와 어긋나는 모양이다. `store.finish`/`recover_on_start` 가 늘 `finished_at` 을 채우므로 실제로 오는 잡은 없다고 주석이 말한다(「확인 못 함」— 옛 DB 흔적 여부). 테스트도 없다(C-3). 죽은 가지면 `assert` 로 못 박든지, 살아 있다면 테스트를 두든지 둘 중 하나.
- **B-3 P2 — 요청마다 마커 전체를 읽는다(상한 없음).** 종료 잡의 `GET /jobs/<id>` 가 이제 `events` 를 매번 질의한다. `events_job(job_id, id)` 인덱스(`store.py:171`)가 있고 G1.13 실측이 마커 450 행 · 문서 50 KB · `real 0.00` 이라 지금은 문제 아니다. 웹은 `app.js:1893/1906` 에서 잡을 열 때 한 번만 부르고 폴링하지 않는다. 다만 `add_markers` 에 행 수 상한이 없어(스텝 300 이 실측 최대일 뿐) 마커를 수만 개 찍는 스크립트는 종료 문서 크기와 응답 시간을 그대로 키운다 — 캐시나 상한을 요구하진 않지만 알고 있어야 한다. 「확인 못 함」: 캐시 없이 두는 것이 결정 49(가장 뜨거운 요청에 짐 안 얹기)의 취지와 맞는지는 `/api/status` 가 이 길로 안 오므로 문제없다고 본다.

- 잘 잠근 것: 활성 `progress` 와 종료 `step_timeline` 의 닫힌 스텝을 **바이트 단위로** 견주는 첫 테스트 · 주입 시계 · v16 모양 재현(`test_the_stored_failed_step_and_last_step_are_never_reconstructed`) · 취소 잡 `ok is not False` · 실제 워커+실제 `rcm wait` 두 개 · mutcheck ㉔ 의 `old` 문자열은 diff 의 서버 본문과 글자 그대로 일치한다(들여쓰기 8칸 포함).
