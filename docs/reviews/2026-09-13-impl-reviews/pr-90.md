판정: 핵심 기능은 명세와 대체로 맞지만, 배포 래퍼에 보안·경합 문제가 있어 그대로 두기엔 어렵습니다. P0는 없고 P1 2건, P2 2건입니다. 코드는 수정하지 않았습니다.

## B. 고쳐야 할 구현 문제

- P1 — 해시 검증 뒤 wheel이 바뀔 수 있습니다. 다운로드는 고유한 `rcm-client.XXXXXX`에 하지만, 검증 뒤 공용 `$TMPDIR/remote_ci_monitor-<version>….whl`로 옮겨 설치합니다. 동일 버전의 서로 다른 dev 서버를 대상으로 래퍼 두 개를 동시에 실행하면 한 프로세스가 검증한 A를 다른 프로세스의 B가 덮어써, A가 검증하지 않은 B를 설치할 수 있습니다. 같은 이름의 기존 사용자 파일도 덮어씁니다. [update-client.sh:32](examples/session/update-client.sh:32), [update-client.sh:36](examples/session/update-client.sh:36), [update-client.sh:43](examples/session/update-client.sh:43)

- P1 — `RCM_TOKEN`이 curl 명령행 인수로 노출됩니다. `Authorization: Bearer …`가 `curl -H`의 argv에 들어가므로, 프로세스 인수를 볼 수 있는 다른 로컬 사용자가 느린 요청 중 토큰을 읽을 수 있습니다. 클라이언트·admin 토큰이면 제출·취소 권한까지 넘어갑니다. [update-client.sh:19](examples/session/update-client.sh:19), [update-client.sh:22](examples/session/update-client.sh:22), [update-client.sh:34](examples/session/update-client.sh:34)

- P2 — health가 503이면 호환성 판정이 조용히 사라집니다. 서버는 janitor stale·worker down에서도 wheel 정보가 든 JSON을 503으로 보내지만, `Client.health()`는 이를 예외로 바꾸고 `rcm check`는 `client` 행을 생략하며 `rcm run`은 경고 없이 계속합니다. 래퍼도 `curl -f`에서 즉시 중단합니다. 재현 조건은 wheel은 정상이나 서버의 다른 health 항목만 실패한 상태입니다. [server.py:1911](src/remote_ci_monitor/server.py:1911), [client.py:503](src/remote_ci_monitor/client.py:503), [cli.py:357](src/remote_ci_monitor/cli.py:357), [cli.py:1357](src/remote_ci_monitor/cli.py:1357), [update-client.sh:22](examples/session/update-client.sh:22)

- P2 — 위의 trailing-slash 별칭이 명세의 정확한 이름 검사를 우회합니다. `/client/<정확한 이름>.whl/`은 마지막 URL 마디가 wheel 파일명이 아닌데도 제공됩니다. [server.py:2137](src/remote_ci_monitor/server.py:2137), [server.py:2446](src/remote_ci_monitor/server.py:2446)

DB·워커 프로토콜·`/api/status` schema v1에는 변경이 없어 그 축의 호환성 문제는 찾지 못했습니다.

## C. 테스트가 잠그지 못한 것

- 성공 경로의 “기동 시 한 번 조립”은 잠기지 않았습니다. 두 응답의 바이트만 비교하므로 요청마다 결정적으로 재조립해도 통과합니다. 실패 경로만 호출 횟수를 셉니다. [test_client_wheel.py:226](tests/test_client_wheel.py:226), [test_client_wheel.py:293](tests/test_client_wheel.py:293)

- 다른 이름 시험에 `<정확한 이름>/`이 없습니다. 현재 mutcheck도 `if name != expected` 자체만 없애므로 앞단의 `/` 정규화 문제를 못 잡습니다. [test_client_wheel.py:244](tests/test_client_wheel.py:244), [mutcheck.py:273](scripts/mutcheck.py:273)

- wrapper 시험은 단일 실행뿐이라 고정 목적지 덮어쓰기·동시 실행·해시 이후 교체를 잠그지 못합니다. 토큰을 환경에서 아예 제거해 argv 노출도 검사하지 않습니다. [test_docs_client_wheel.py:88](tests/test_docs_client_wheel.py:88), [test_docs_client_wheel.py:104](tests/test_docs_client_wheel.py:104)

- health 503이면서 `client_wheel`은 정상인 조건의 `check`·`run`·wrapper 시험이 없습니다. 현재 조립 실패 시험은 health 200만 다룹니다. [test_client_wheel.py:273](tests/test_client_wheel.py:273)

- 자동 시험의 설치는 로컬 wheel 경로 또는 curl로 받은 파일을 사용합니다. 명세의 실제 `pip install http://…whl`은 수용 보고서에서 한 번 실측했지만 CI 회귀 시험으로 잠기지 않았습니다. [test_client_wheel.py:182](tests/test_client_wheel.py:182), [m5i-verify-client.md:14](docs/acceptance/reports/2026-09-10-m5i-verify-client.md:14)

- `min_client_version = 0.2.0`이지만 실제 교차 버전 실측은 0.2.4뿐입니다. 0.2.0 클라이언트의 전체 run/wait 호환성은 확인 못 함입니다. [clientwheel.py:31](src/remote_ci_monitor/clientwheel.py:31), [m5i-verify-client.md:18](docs/acceptance/reports/2026-09-10-m5i-verify-client.md:18)
