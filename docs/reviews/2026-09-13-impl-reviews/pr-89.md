- **A-1. `serve`·`worker` 에는 유효 `data_dir` 계산을 적용하지 않았다.** 결정 75 는 「`serve`·`worker` 기존 규칙 + token」이라 문면상 위반은 아니지만, §3 B2-5(156행)의 「**쓰기 명령은** CLI 와 같은 우선순위로 유효 `data_dir` 을 계산한다」의 「쓰기 명령」에 `serve` 가 빠질 이유는 없다. 결과: `rcm serve --config <운영 설정의 사본(data_dir 만 운영)>` → **None(허용)**, `RCM_SERVER_DATA_DIR=<운영> rcm serve --config <시험 설정>` → **None**, `rcm worker --config <사본>` → None(재현: 위 픽스처로 확인). `_server_verdict`(497~528행)는 `--data-dir` 와 `--config` 의 **경로가 운영 안인지**만 본다. 「두 서버, 한 SQLite」(505행의 문구)를 막는 규칙이 설정 사본엔 안 통한다. → B-2.

## B. 고쳐야 할 것

### P1

- **B-1. 워크트리 venv 를 활성화한 셸에서는 규칙이 스스로를 무력화한다.** `find_production._venv_of_rcm`(560~566행)은 「PATH 의 `rcm` 이 있는 venv」를 **운영 venv 로 정의**한다. `_db_write_verdict` 472~474행은 실행 파일이 그 venv 안이면 면제한다. 둘이 같은 PATH 를 보므로 맨 `rcm` 은 **언제나 「서비스 자신」**이다. 정상 PATH(이 Mac: `~/.local/bin/rcm → ~/.local/share/rcm-venv/bin/rcm`, 심링크라 `realpath` 가 venv 를 찾는다)에서는 그게 맞는 답이다. 그러나 사용자가 `source .venv/bin/activate` 한 셸에서 Claude Code 를 띄우면 PATH 의 `rcm` 은 워크트리 것이고, 그러면 (1) 발견이 `prod.venv = <워크트리>/.venv`, `prod.checkout = <워크트리>` 로 잘못 잡히고 (2) `rcm token --config ~/.config/rcm/server.toml add x` 는 `_executable` 이 `prod.venv` 안이라 **None(허용)** — 정확히 2026-09-10 의 사고 모양이다. 재현: `Production(venv=WT/.venv, …)` + `_which → WT/.venv/bin/rcm` 로 `bash("rcm token --config /srv/rcm/config/server.toml add x")` → None(확인). 발견의 전제(모듈 docstring 6~8행)는 #89 이전부터 있었지만, #89 는 그 전제에 **면제 규칙**을 얹어 실패 모드를 「막지 않음」에서 「위험한 것을 허용」으로 바꿨다. 활성화 셸이 실제로 얼마나 흔한지는 **확인 못 함**(이 세션의 PATH 는 정상). 보완 후보: 발견 단계에서 `direct_url.json` 의 editable 원본이 `main` 체크아웃(운영 폴더)인지·`.venv` 가 워크트리 안인지로 교차 검증하거나, 후보 venv 가 `pyvenv.cfg` 만이 아니라 launchd/systemd 유닛의 경로와 맞는지 보는 것.

### P2

- **B-2. 설정 사본·env 덮어쓰기로 운영 DB 를 여는 `serve`·`worker` 를 안 막는다**(A-1). 재현: 위. `_server_verdict` 가 `_effective_data_dir` 를 쓰면 같은 코드로 닫힌다. `worker` 는 `--data` 가 워크스페이스 디렉터리라 DB 는 아니지만 `_server_verdict` 가 이미 `prod.data_dir` 와 비교한다.
- **B-3. 셸 문법 몇 가지가 조각 분해를 그대로 통과한다.** `_split_segments`(149~176행)·`_argv`(198~214행)는 `;`·`&&`·`||`·`|`·개행과 앞머리 `sudo`·`env`·`VAR=` 만 안다. 다음은 전부 **None(허용)** 이었다(모두 `--config <운영>`): `(rcm token … list)`(서브셸 — `argv[0]` 이 `(rcm`), `{ rcm token …; }`, `exec rcm token …`, `command rcm …`, `nohup rcm …`, `time rcm …`, `bash -c '…'`, `sh -lc "…"`, `echo $(rcm token … add x)`, `xargs … rcm token …`, `uv run rcm …`, `rcm --config <운영> token list`(하위 명령 앞의 전역 옵션 — 실제 CLI 에는 전역 `--config` 가 없어 어차피 argparse 오류지만). 이 가드는 실수 방지용이지 적대자 방어가 아니므로 P2 로 두지만, `(cd … && rcm …)`·`exec`·`nohup`·`time` 은 에이전트가 흔히 쓰는 모양이다. `_argv` 의 앞머리 목록에 `exec`·`command`·`nohup`·`time` 을 더하고, 조각 시작의 `(`·`{` 를 벗기는 것만으로 대부분 닫힌다.
- **B-4. `env` 의 플래그 형태가 판정을 통째로 끈다.** `_argv` 는 `env` 를 떼지만 `-i`·`-u NAME`·`--` 는 안 뗀다 → `argv[0]` 이 `-i`/`-u`/`--` 가 되어 `_rcm_subcommand` 가 None. 재현: `env -i PATH=/x rcm token --config <운영> list` → None, `env -u RCM_CONFIG rcm token --config <운영> list` → None, `env RCM_CONFIG=<운영> -- rcm token list` → None. `_env_of`(179~195행)도 `-u` 뒤의 이름을 건너뛰지 않는다. 특히 `env -u RCM_CONFIG` 는 시험 설정을 잠시 벗어나려는 사람이 정말 쓸 법한 형태다.
- **B-5. 심링크 별칭은 못 본다.** `inside()`(123~131행)는 `normpath` 만 쓴다. `--data-dir <운영 data_dir 로 가는 심링크>` → None(재현: 임시 디렉터리에 `link → /srv/rcm/data` 만들고 `cwd=tmp`, `rcm token --data-dir link list`). macOS 의 `/tmp`↔`/private/tmp`, `/var`↔`/private/var` 같은 별칭도 같은 구멍이다. 운영 `data_dir` 이 심링크를 거치는지는 **확인 못 함**(`~/.local/share/rcm` 을 열지 않았다). `_as_path` 뒤에 `os.path.realpath` 를 한 번 더 두면 되지만 순수 함수 `decide()` 가 파일계를 보게 되므로 발견 단계에서 `prod.data_dir` 의 realpath 를 함께 들고 다니는 편이 낫다.
- **B-6. `cd <디렉터리> && rcm token …` 은 바뀐 cwd 를 모른다.** `_bash_verdict` 는 조각마다 세션 cwd 를 그대로 쓴다. `cd <rcm.toml 이 있는 워크트리> && rcm token list` → **deny**(오탐 — CLI 는 그 폴더의 `./rcm.toml` 을 집는다). 반대로 세션 cwd 에 `rcm.toml` 이 있어 `local_config=True` 인데 `cd /elsewhere && rcm token list` 면 **None** 인데 CLI 는 운영 설정까지 내려간다(미탐). `serve` 규칙도 같은 약점을 처음부터 갖고 있었다.
- **B-7. `XDG_CONFIG_HOME` 은 운으로 맞는다.** `XDG_CONFIG_HOME=<시험 xdg> rcm token list`(그 안에 `rcm/server.toml`, data_dir 시험) → **deny** — `_effective_data_dir` 451~455행이 `--config`·`RCM_CONFIG`·`./rcm.toml` 다음을 곧장 `prod.data_dir` 로 보기 때문이다. CLI 는 XDG 를 `~/.config/rcm` 보다 먼저 본다(config.py 387~388행). 오탐이고 드문 사용이라 P2. `_config_dir()`(586~593행)의 발견은 XDG 를 보므로 판정 쪽만 빠졌다.
- **B-8. `$VAR` 이 든 경로는 훅 프로세스의 환경으로 펼친다.** `_as_path` 115행 `os.path.expandvars` — `rcm token --data-dir "$X" list` 에서 `X` 가 훅에 없으면 문자 그대로 `$X` 가 되어 None. 셸에서 `X=<운영>` 으로 정의된 뒤 같은 명령줄에 있으면(`X=/srv/rcm/data; rcm token --data-dir $X list`) 조각이 나뉘어 못 본다. 실수 방지 범위에선 감수할 만하다.
- **B-9. `prod.venv` 를 못 찾으면 서비스 자신의 `rcm` 도 막는다.** `_venv_of_rcm` 이 None(예: `~/.local/bin/rcm` 이 심링크가 아니라 pipx 셈 같은 사본)이면 472행 면제가 절대 참이 아니고, 메시지는 `the service's own rcm` 이라는 허깨비 이름을 준다(478행). 안전한 방향의 오탐이라 P2. 이 Mac 은 심링크라 해당 없음.
- **B-10. 설정 파일의 `data_dir` 에 `expandvars` 를 적용한다**(421행). CLI 의 `ServerConfig.data_dir`(config.py 182~183행)는 `expanduser` 만 한다. `data_dir = "$HOME/rcm"` 같은 값은 CLI 에선 문자 그대로 `$HOME/rcm`(cwd 상대)이고 가드에선 홈이 된다. 오탐·미탐 어느 쪽으로도 실제 영향은 거의 없지만 「CLI 와 같은 우선순위」라는 docstring(428행)과 어긋난다. 상대 `data_dir = "data"` 도 CLI 는 프로세스 cwd 기준인데 가드는 상대 경로 그대로 비교해 언제나 밖이다.

### 특기(문제 아님)

- `-c` 를 `--config` 의 별칭으로 본다(441·500행) — CLI 에 `-c` 는 없다. 무해.
- `python`(3 없이)이 PATH 에 없으면 `_executable` 이 None → 면제 없이 계속 판정 → deny. fail-closed 방향이라 맞다. `_which` 가 None 인 `rcm` 도 같다.
- 따옴표(`'…'`, `"--config=…"`, `--config="…"`), `--config=` 형, 하위 명령 뒤의 옵션(`rcm token list --config …`), `--data-dir …/`, `…/../data`, 리다이렉션(`2>/dev/null`, `>out`), 파이프 뒤 `| head`, 백슬래시 개행, `RCM_CONFIG='…'` — 전부 deny(확인). `rcm token --help`·`rcm token add x --help`·`add -h` 는 None.
- `_which` 오분류: `realpath` 로 풀어 venv 안인지만 본다. 심링크 셈(`~/.local/bin/rcm`)은 맞게 풀린다. 오분류 가능한 경우는 B-1 뿐이다.
