## B. 고쳐야 할 구현 문제

### P1 — 상대 `PATH`에서 다른 디렉터리를 검사해 preflight가 거짓으로 통과할 수 있음

- 위치: `src/remote_ci_monitor/runner.py:88-96,198-205`
- 재현 조건:

  1. 프리셋에 `requires=["fvm"]`, `PATH="tools:/usr/bin:/bin"` 설정.
  2. `rcm serve`의 현재 작업 디렉터리에는 `tools/fvm`이 존재.
  3. 잡 워크스페이스에는 `tools/fvm`이 없음.
  4. argv는 `/bin/sh`처럼 절대경로로 시작하고, 스크립트가 `fvm` 실패 시 다른 SDK로 폴백.

- `shutil.which()`는 서버/워커 프로세스의 현재 디렉터리를 기준으로 `tools/fvm`을 찾아 통과시킵니다. 실제 프로세스는 `cwd=spec.workspace`에서 실행되므로 같은 `PATH`가 다른 파일을 가리킵니다.
- 결과적으로 이 기능이 막으려던 “도구가 없는데 다른 SDK로 초록”이 다시 가능합니다.
- 반대 배치에서는 도구가 워크스페이스에 있는데도 `tool_missing`으로 거짓 실패합니다.
- 빈 PATH 구성요소(`:`, 앞·뒤 `:`)도 같은 cwd 차이를 만듭니다.

### P1 — basename이 없는 절대경로가 공개 상태로 노출됨

- 위치: `config.py:431-446`, `runner.py:62-65`, `worker.py:475-483`
- 재현 조건: `requires=["/Users/build/private-sdk/"]` 또는 `requires=["/"]`.
- 해당 경로는 실행 파일이 아니므로 검사에 실패하고, `public_name`이 원래 경로로 돌아갑니다.
- 결과: `summary`, `summary_args`, `GET /jobs/<id>`, 공개 설정의 `/api/status.recent`에 서버 경로가 노출됩니다.
- 명세의 “args는 이름만”과 보안 경계를 직접 위반합니다.

### P1 — 정상적인 절대경로 선언도 잡 로그에 노출됨

- 위치: `runner.py:99-103,184-192`
- 재현 조건: `requires=["/opt/private/toolchains/fvm"]`인 잡을 한 번 실행.
- 성공·실패 모두 원문 절대경로가 토큰 보호 잡 로그에 기록됩니다.
- 공개 API 노출보다는 범위가 좁지만, 명세가 로그까지 명시적으로 금지합니다.

### P2 — 자재화 중 취소·종료 요청을 `tool_missing` 실패가 덮을 수 있음

- 위치: `runner.py:175-194`, `worker.py:471-484`, `remote_worker.py:485-521`, `store.py:1883-1919`
- 재현 조건:

  1. git fetch나 큰 트리 해제처럼 자재화가 오래 걸리는 잡이며 `requires` 중 하나가 없음.
  2. 자재화 도중 사용자가 취소하거나 워커가 종료됨.
  3. 자재화가 끝난 뒤 preflight가 누락 도구를 발견.

- preflight 전에 `observer.should_cancel()`/`should_stop()`을 확인하지 않습니다.
- 로컬 catch는 현재 상태를 재조회하지 않고 곧바로 `FAILED`로 마감합니다.
- `Store.finish()`도 `only_from`이 없으면 `cancelling`을 `failed`로 바꿀 수 있습니다.
- 원격 경로도 같은 방식으로 `failed` finish를 보냅니다.
- 결과: 사용자가 취소한 잡이 `cancelled`/exit 2가 아니라 `tool_missing`/exit 1로 끝납니다.

자원 누수나 DB 마이그레이션·옛 클라이언트 파손은 이 diff에서 추가로 확인되지 않았습니다.

## C. 테스트가 잠그지 못한 것

- `tests/test_requires.py:126-143`에 `/`, `/opt/bin/` 같은 basename 없는 절대경로 설정 사례가 없습니다. 원격 finish만 `/opt/bin/`을 거부합니다.
- `tests/test_requires.py:166-181,270-281`은 절대경로 로그 노출을 허용하도록 단언해 명세 위반을 고정합니다.
- 상대·빈 구성요소가 포함된 `PATH`와 서버 cwd/잡 workspace가 다른 경우가 없습니다.
- 자재화 콜백을 막아 둔 상태에서 취소·shutdown을 넣고, 이후 누락 도구를 반환하는 경쟁 테스트가 없습니다.
- `tests/test_requires_check.py:60-67`도 `/bin/sh`가 그대로 출력되는 것을 정답으로 잠급니다.
- `tests/test_requires.py:461`의 `os.environ["PATH"] not in log` 형태는 PATH 전체 문자열만 검사합니다. 개별 PATH 구성요소 하나가 노출되어도 통과할 수 있는 약한 단언입니다.
- 문서 테스트 `tests/test_docs_m5j_requires.py:25-43`은 단어 존재만 확인하므로 “no path”와 “declared path는 출력”이라는 상충 문장을 잡지 못합니다.
- 옛 워커 테스트는 키 없는 finish 수용만 검사합니다. claim을 받은 옛 워커가 `requires`를 무시하고 실제로 프로세스를 실행하는 호환 동작은 단위 테스트로 잠기지 않았고 수용 보고서의 수동 실측에만 있습니다.
- mutcheck는 “검사를 전부 생략”하는 변이 하나뿐입니다. 상대 PATH 기준 cwd, 공개 basename 폴백, 취소 우선순위를 각각 변이로 추가할 만합니다.
