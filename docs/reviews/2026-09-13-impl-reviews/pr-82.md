## B. 버그 · 오류 경로 · 수집기의 사각

질문받은 것부터. **「`addScriptToEvaluateOnNewDocument` 전에 던져진 오류를 놓치나」** — 수집기는 `Chrome.__init__`(`test_web_browser.py:160-166`)에서 첫 `Page.navigate` 보다 먼저 설치되고, 새 문서마다 페이지 스크립트보다 앞서 돈다. 초기 `about:blank` 만 예외인데 거기엔 앱 코드가 없다 → 사각 아님. **「워커 안의 오류」** — `app.js` 에 `new Worker` 가 없다(grep) → 해당 없음. `EventSource` 의 `onerror` 는 앱이 `onSseError()` 로 처리하는 연결 이벤트라 예외가 아니다.

1. **P2 — 수집기가 설치됐는지 아무도 확인하지 않는다(테스트 하네스의 fail-open).** `page_errors()`(`test_web_browser.py:225-231`)는 `Array.isArray(window.__rcmErrors) ? window.__rcmErrors : []` 라 수집기가 **없으면** 빈 목록을 돌려주고, 테스트는 `== []` 를 단언해 통과한다. **실측(mutant M2)**: `__init__` 의 `addScriptToEvaluateOnNewDocument` 호출을 지우고 `-k "local_host_card or remote_worker_sample"` 를 돌리면 **2 passed**. 즉 수집기가 사라져도(CDP 메서드 이름 오타, Chrome 이 스크립트를 거부, 누가 정리하며 지움) I5 의 「0건 단언」은 아무것도 지키지 않는다. 고치는 법: `ready_js` 가 참이 된 뒤 `window.__rcmErrors` 가 배열이 **아니면** 실패(`None` 을 돌려주고 호출자가 단언), 그리고 `scripts/mutcheck.py` 에 「수집기 설치 제거」 mutant 를 더한다(명세 §8 이 이 PR 에는 mutant 를 안 두었다).
2. **P2(부분 확인) — `fetchStatus()` 의 `.catch` 가 render 예외를 삼킬 수 있는 경로.** `app.js:1039-1063`: `api("/api/status").then(…).then(function (doc) { …; render(); }).catch(function () { renderHeaderConn(); })`. 이 사슬 안에서 `render()` 가 던지면 `.catch` 가 받아 unhandledrejection 이 **되지 않는다**. **실측(mutant M1)**: `app.js:1730` 을 `var js = local ? …` 로 되돌리고 `-k local_host_card` 를 돌리면 `AssertionError: page raised while loading …: ['unhandledrejection: local is not defined']` — 즉 지금의 B1 은 수집기에 잡힌다(초기 로드는 `app.js:2092` 의 `first = verifyToken(…).then(fetchStatus)` 사슬이라 바깥 프로미스가 거부되는 것으로 보인다 — 어느 프로미스가 거부됐는지는 **확인 못 함**). 그러나 폴링(`:1089 setInterval → fetchStatus()`)·SSE 재조회(`:1037 scheduleRefetch`) 경로의 render 예외는 `.catch` 에서 끝나 수집기에 안 보이고 「page not ready」 타임아웃으로만 드러난다. 「원인이 선명하다」는 이 PR 의 약속은 첫 렌더에만 성립한다. 고치려면 `.catch` 핸들러가 `e instanceof Error` 면 `window.dispatchEvent(new ErrorEvent("error", {error: e, message: e.message}))` 로 되던지거나(앱 코드), 수집기가 `console.error` 도 후킹하도록(테스트 코드) 하면 된다.
3. **P2 — `page_errors()` 는 한 번 찍는 스냅샷이다.** 두 테스트 모두 `open()` 이 끝난 직후 한 번 읽는다. `?poll=1` 이라 그 뒤의 재렌더(1초 폴링)는 안 본다. B1 은 첫 렌더에서 터지므로 지금은 충분하다.
4. **P2 — `chrome_is_required_where_rcm_chrome_is_set` 가 autouse 픽스처라 pytest 는 `ERROR`(setup) 로 보고한다**(검증 V1.4 가 적었다). 종료 코드 1 이고 skip 이 아니므로 결정 79 의 뜻은 지켜진다. 오너 판단.
5. **확인 못 함 — `status_until(…, timeout=5.0)` 이 청소기의 첫 측정(`job_storage.volume_bytes`)을 5초 안에 요구한다.** tmp_path 라 빠르지만 느린 러너에서 플레이크가 될 수 있다. dev CI 로그에서 이 테스트의 실패는 못 봤다(실패한 것은 #98 의 찬 기동 쪽 `test_desktop_dom_…` 뿐).
6. **문제 없음 —** `find_chrome()` 에서 `RCM_CHROME` 이 상대 경로이면 `Path(env).is_file()` 은 cwd 기준 — CI 는 이름(`google-chrome`)을 넘기므로 `shutil.which` 경로. 
7. **보안 —** 테스트의 `DISK["path"]` 는 가짜 경로. 실제 `/api/status` 의 `disk.path` 노출은 #84 리뷰에서 다룬다(이 PR 이 만든 문제는 아니다).

## C. 테스트가 잠그지 못한 것

- B1 위(수집기 존재) — mutant M2 가 초록. **mutcheck 후보 1순위.**
- B2 위(재조회 경로의 render 예외) — 잠글 수 없는 게 아니라 앱 쪽 `.catch` 의 설계 문제.
- `(line,) = got["substats"]` 로 substat 이 **정확히 하나**임을 잠근 것, `substat_cards == ["macmini"]` 로 워커 카드에 회계 줄이 없음을 잠근 것은 좋다(원격 표본에 `disk` 를 넣어 `disk_meters == 2` 까지).
- `find_chrome()` 의 「`RCM_CHROME` 이 있으면 다른 후보로 안 넘어간다」는 단위 테스트가 없다(검증 V1.4 가 손으로 확인). 한 줄짜리 monkeypatch 테스트면 된다. P2.
