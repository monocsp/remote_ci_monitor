## B. 문서가 약속하는 것 vs 코드가 하는 것

1. **P1 — 예시의 `flock` 이 macOS 에 없다 → 락 없이 heavy 구간이 도는 fail-open.** 절의 셸 예시:
   ```sh
   exec 9>/tmp/gate-heavy.lock
   flock 9            # waits while another gate job is in its heavy section
   flutter test ...
   ```
   `flock(1)` 은 util-linux 의 명령이라 macOS 에는 없다(이 Mac: `which flock` → not found; 있는 것은 `/usr/bin/lockf`·`/usr/bin/shlock`). 이 요청의 출처는 **맥미니**에서 Flutter 게이트를 돌리는 팀이고(workplan 머리글) 이 레포의 빌드 머신도 Mac 이다. 예시대로 넣으면 `flock: command not found` 로 그 줄만 실패하고(대상 스크립트 `local_ci.sh` 가 `set -e` 없이 `echo FAIL:` 을 67곳 쓰는 스타일이라 계속 진행한다 — workplan I1), `flutter test` 는 **락 없이** 돈다 — 이 절이 막으려던 바로 그 상황이고, 문서를 잠근 테스트 `test_the_experiment_needs_a_lock_in_the_script` 는 `flock\|machine-wide lock` 문자열만 봐서 초록이다. 고치는 법: macOS 는 `lockf -k /tmp/gate-heavy.lock flutter test …`(또는 `python3 -c 'import fcntl…'`), Linux 는 `flock`, 그리고 **락 명령의 실패를 중단으로**(`flock 9 \|\| exit 3`) 하라고 적는다. 「락이 걸렸는지 확인하는 방법」(두 잡을 올려 `step_timeline`/로그 시각으로 heavy 구간이 겹치지 않음을 본다)도 한 줄.
2. **P1 — `concurrent_at_start` 는 어디에도 노출되지 않는다.** 문서: 「the `concurrent_at_start` field on each job says how many jobs were running when it started, so the effect can be measured afterwards」. 코드: `store.py:113`(v10 열) · `:1764`(claim 때 기록) · `:1789 def concurrent_at_start(self, job_id)`(getter) — **getter 를 부르는 곳이 없고**, `server.py`·`cli.py`·`core/render_text.py`·`web/app.js` 어디에도 그 키가 없다(grep `concurrent_at_start` in `src/` → `store.py` 5곳뿐). `/jobs/N`·`rcm jobs --json`·`/api/status` 어느 것도 이 값을 주지 않는다. 문서가 「field on each job」이라고 하면 사용자는 JSON 에서 찾는다. 이 PR 에서 노출하거나(`/jobs/N` 응답에 키 추가 — 스키마 v1 은 키 추가 허용), 「DB 에 기록되지만 아직 보이지 않는다(`sqlite3 … SELECT concurrent_at_start FROM jobs`)」로 고쳐 쓴다.
3. **P1(순서) — `step_timeline` 은 G1(#108, 열림)이다.** 문서·테스트(`test_measurement_hooks_are_named` 가 `step_timeline` 문자열을 요구)가 아직 없는 필드를 약속하고 잠근다. workplan §3 순서는 G4 → G1 → **G3 문서**다. #108 뒤에 머지하거나, 그 문장을 「G1 이 들어오면」으로 고치거나 뺀다. #108 이 먼저 머지되면 이 항목은 소멸한다.
4. **P2 — 「next job's light phase overlaps the current job's heavy phase」는 admission 과 맞물리는 조건을 빠뜨렸다.** `admission = "load"` 에서 레인 2 는 CPU 가 `cpu_max_percent`(기본 80 %, `config.py:88`) 이하인 표본이 `admission_samples`(3) 연속일 때만 claim 하고, 지나면 `admission_cooldown_seconds`(30 s) 쉰다. 즉 A 가 heavy(테스트 ~100 %) 인 동안 B 는 **들어오지 못한다**. 실제로 얻는 겹침은 「A 의 light 구간 동안 B 가 들어와 둘의 light 가 겹치고, 둘 다 heavy 에 닿으면 락이 순서를 정한다」이다. 문장이 이렇게 말해야 사용자가 「왜 B 가 안 뜨나」를 admission 로그(`server.py:364-367` 기동 줄 「lane 1 always claims」)에서 찾는다. 같은 절 위의 「Admission」 본문이 이 규칙을 이미 설명한다면 상호 참조 한 줄이면 된다(그 본문은 확인 못 함 — diff 밖).
5. **P2 — `/tmp/gate-heavy.lock` 은 머신 전체 락이다** — 같은 머신에서 `rcm serve` 의 레인과 `rcm worker` 의 레인이 함께 돌 때(바로 위 문단이 다루는 배치) 둘 다 이 락을 공유하므로 좋다. 그 점을 한 문장 적으면 위 문단과 이어진다. 또한 `exec 9>` 로 fd 를 여는 예시는 스크립트가 서브셸·`exec` 로 다른 프로그램을 덮어쓰면 락이 상속된다는 것도 헤더에 한 줄.
6. **문제 없음 —** `admission = "load"` 는 이미 기본값(`config.py:87`)이라 TOML 예시는 명시일 뿐. `argv = ["/bin/bash", "scripts/local_ci.sh"]` 형식은 다른 절과 같다. `concurrency_group` 을 빼면 서버 상호배제가 사라진다는 말은 코드와 맞다(`config.py:577-638`, 스케줄러의 group 검사).
