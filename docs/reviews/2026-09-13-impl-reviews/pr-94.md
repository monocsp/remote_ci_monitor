## A. 명세와 맞는가

맞는다. 결정 74 의 「거절 메시지가 복원 절차를 가리킨다」는 `newer_database_message` 가 만들고, #94 는 그 문장이 **트레이스백 없이 한 줄로** 나오게 했다. `StoreError` 두 경로(백업 실패 682~686행 · 새 스키마 667행) 모두 `cmd_serve` 1148~1152행 · `cmd_token` 1575~1578행에서 잡힌다. 종료 코드 2(`USAGE_EXIT`)는 CHANGELOG 가 명시했다.

## B. 고쳐야 할 것

### P1

- **B-1. `serve` 는 포트를 잡기 전에 DB 를 마이그레이션한다 — 실패 문장이 사실을 숨긴다.** `server.serve` 2656~2660행: `mkdir` → `Store(...)`(마이그레이션) → `App` → `make_server`(bind). 운영 서비스가 도는 동안 새 빌드로 `rcm serve --config <운영>` 을 치면 DB 가 **먼저 v16 으로 올라가고** 그 다음 `cannot start server: Address already in use`(1146~1147행, exit 2)가 찍힌다. 문장은 「못 떴다」고만 말하고 DB 가 이미 바뀌었다는 말이 없다 — 옛 서비스는 다음 재시작에서 못 뜬다(2026-09-10 의 모양 그대로). #94 이전부터 있던 순서이고 #94 는 문장 모양만 다뤘으니 범위 밖이지만, **이 PR 이 만든 문장이 그 오해의 자리**다. 재현: 시험 설정으로 서버를 띄운 채 같은 설정·다른 빌드로 `rcm serve` — 이 리뷰에서는 코드 순서로만 확인했다(두 빌드를 띄우진 않음). 가드(#89)는 `rcm serve --config <운영>` 을 막지만 설정 사본은 못 막는다(89.md B-2). 고치는 자리는 `serve()` 에서 bind 를 `Store` 앞으로 옮기는 것(`make_server(app)` 이 `app` 을 받으므로 `App` 생성을 둘로 나누거나 소켓을 먼저 여는 정도).

### P2

- **B-2. `sqlite3.Error` 는 여전히 트레이스백이다.** `Store.__init__` 이 던지는 것 중 `StoreError` 로 감싸인 건 백업 실패와 새 스키마뿐이다. 실제 실행:
  - 깨진 `rcm.sqlite3`(첫 바이트가 SQLite 헤더가 아님) → `database_version` 357행에서 `sqlite3.DatabaseError: file is not a database` → `token` **rc=1 트레이스백**, `serve` 도 트레이스백.
  - 읽기 전용 `data_dir`(`chmod 500`) + 현재 버전 DB → `_conn` 607행 `PRAGMA journal_mode=WAL` 에서 `sqlite3.OperationalError: attempt to write a readonly database` → 둘 다 트레이스백.
  - 마이그레이션 SQL 자체의 실패(`_MIGRATIONS[target]` 실행 중 `sqlite3.Error`) → ROLLBACK 뒤 재발생 → 트레이스백(백업은 남는다).
  CHANGELOG 제목 「refuse in one line when the database cannot be opened」는 이 경우들을 약속하는데 본문은 「a migration backup that could not be written, or a database a newer build has migrated」로 좁힌다. 제목이 넓고 구현이 좁다. `except (StoreError, sqlite3.Error)` 한 줄이면 닫힌다(`cli.py` 는 이미 `sqlite3` 를 import 해 `_offline_gc` 761행에서 같은 처리를 한다).
- **B-3. `token` 과 `serve` 의 `OSError` 처리가 다르다.** `cmd_serve` 는 `OSError` 를 잡아 한 줄(1146~1147행)이지만 `cmd_token` 은 안 잡는다. 실행: `data_dir` 이 파일 → `Store.__init__` 599행 `mkdir` 의 `FileExistsError` → `serve` 는 `rcm: cannot start server: File exists`, `token` 은 **트레이스백**. 부모를 만들 수 없는 경로(`/System/…`) → `serve` 는 `Operation not permitted` 한 줄, `token` 은 `PermissionError` 트레이스백. 같은 PR 이 두 명령을 「같은 모양으로」 고쳤다고 했으니 `cmd_token` 에도 `except OSError` 가 있어야 한다.
- **B-4. 종료 코드 2 의 의미.** 이 CLI 에서 2 는 「사용법·설정」, 3 은 「모른다」다(`EXIT_UNKNOWN`; `_offline_gc` 는 새 스키마 DB 를 만나면 `newer_database_message` + **exit 3**, 749~751행). 같은 문장을 `rcm token` 은 exit 2 로 낸다. 서버를 못 띄운 것을 2 로 두는 건 기존 `OSError` 경로와 맞고, 마이그레이션 백업 실패도 「설정·환경을 고치라」는 뜻이라 2 가 어울린다. 다만 같은 `newer_database_message` 가 명령에 따라 2/3 으로 갈리는 점은 문서 어딘가에 적히면 좋다. 바꿀 것까지는 아니다.
- **B-5. `serve` 의 `StoreError` 문장 앞에 `warning: no [[presets]] configured` 가 먼저 나올 수 있다**(1142~1143행이 `serve()` 보다 앞). launchd 로그에서 「한 줄」을 찾는 운영자는 마지막 두 줄을 보게 된다. 테스트의 `len(err.strip().splitlines()) == 1` 은 프리셋이 있는 설정으로만 돌아 이걸 못 본다. 사소하다.

### 특기(문제 아님)

- `cmd_token` 의 `try/except` 배치: `Store(...)` 실패 시 `store` 가 정의되지 않은 채 `finally: store.close()` 로 가지 않도록 두 `try` 로 나눴다 — 맞다.
- 다른 프로세스가 `BEGIN IMMEDIATE` 로 쓰기 잠금을 쥔 채 `rcm token list` → 읽기라 즉시 성공(0.08 s). 쓰기(`add`)는 `busy_timeout=5000` 뒤 `sqlite3.OperationalError: database is locked` 가 될 텐데(B-2 와 같은 구멍) 이 리뷰에선 돌리지 않았다 — **확인 못 함**.
- `StoreError` 를 `add`/`revoke` 도중(중복 이름 2049행)에 받으면 이미 `_usage` 한 줄이었다(`rcm: token 'x' already exists`, 확인). #94 는 열 때만 더했다.
- 문장에 백업 경로가 들어간다(`restore <data_dir>/backup/rcm.sqlite3.v16.bak`). 「상태·오류·로그에 경로 금지」는 API/`/api/status` 규칙이고 운영자 stderr 는 복원 절차를 가리키는 게 목적이라 맞다.

## C. 테스트가 잠그지 못한 것

- B-2·B-3 의 경로가 하나도 없다: 깨진 파일 · `data_dir` 이 파일 · 읽기 전용 `data_dir`. 세 개 다 `tmp_path` 로 1분짜리다.
- `token` 은 `list` 만 돈다. `add`·`revoke` 도 같은 `Store(...)` 를 지나므로 결과는 같지만, parametrize 에 넣는 비용이 0 이다.
- 백업 실패 테스트는 `_copy_database` 를 monkeypatch 해 `ENOSPC` 를 흉내 낸다 — 실제 V2.8 은 `chmod 500 backup/` 이었다. 둘 다 `_backup_before_migration` 의 같은 `except Exception` 으로 들어가므로 동치지만, monkeypatch 는 `_copy_database` 가 `_backup_before_migration` 에서 **모듈 전역으로** 호출된다는 구현 세부에 묶인다(지역 import 로 바꾸면 테스트가 조용히 아무것도 안 흉내 내고 통과한다 — DB 가 정상 마이그레이션되어 `version_of(db) == DB_VERSION - 1` 이 실패하긴 하니 완전히 조용하진 않다).
- `assert "Traceback" not in err` 는 좋다. `rc == USAGE_EXIT` 도 잠근다. mutcheck 로 잡을 만한 것: `except StoreError` 를 지우면 두 테스트 다 빨개진다(트레이스백이 `main()` 밖으로 나가 pytest 가 예외로 잡는다) — 잠겨 있다.
- B-1 (bind 전 마이그레이션)은 테스트가 없다 — 포트를 먼저 점유하고 `rcm serve` 를 낮은 버전 DB 로 부른 뒤 `version_of(db)` 가 **그대로**여야 한다는 테스트가 그 수정의 잠금이 된다.
