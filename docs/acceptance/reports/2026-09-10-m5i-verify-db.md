## 비고

1. **V2.1 의 워크스페이스는 손으로 남겼다.** 프리셋이 `ok`(`true`) 하나라 성공 잡의 워크스페이스는 잡 종료에 지워진다(`keep_workspace_on_failure` 는 실패에만). 표에 잡이 나오려면 `workspaces/<id>/` 가 있어야 해서 tests/test_offline_gc.py 픽스처와 같은 모양으로 종료 잡 셋에 64 KiB 파일을 두었다. 「서버가 WAL 을 쥔 채 사본 위에서 계획한다」는 검증에는 영향 없다 — 잡 행은 실제 서버가 쓴 것이다.
2. **`_verify_copy` 는 깨끗하다.** V2.6 기동 직후 `backup/` 에는 `rcm.sqlite3.v15.bak` 하나뿐이었다(코드 주석의 「읽기 전용 연결이 `-wal`·`-shm` 을 못 지운다」 함정을 보통 연결로 피한 것이 실기로 확인됨).
3. **`backup/` 의 `rcm.sqlite3.v15.bak-wal`·`-shm` 은 내 측정이 남긴 것이다.** macOS 의 `sqlite3` CLI 로 `.bak` 의 `PRAGMA user_version`·`integrity_check` 를 읽으면 WAL 헤더 파일 옆에 `-wal`·`-shm` 이 남는다(스크래치 사본으로 재현: CLI 는 남기고, python `sqlite3.connect` 는 안 남긴다). 서버가 만든 것이 아니다. `_prune_backups` 의 정규식은 `.v<N>.bak` 만 보므로 이 찌꺼기는 세지 않는다.
4. **V2.5 뒤의 0 바이트 `-wal`·`-shm`** 은 `database_version()` 의 `mode=ro` 연결이 남기는 것으로, 코드 주석이 이미 밝힌 무해한 부작용이다(「읽기만 한다」는 명령이 데이터 디렉터리에서 지우지 않는다는 결정). 원본 DB 파일은 그대로다.
5. **결정 80 의 요약 줄과 문서의 백업·정지 순서.** `docs/gate-replay-fixes-workplan.md` §7 결정 80 은 「… drain 확인 → 백업 → 정지 → pull …」이고, `docs/operating.md` 「Upgrade」와 같은 계획서 §6 은 「정지 → 정지 직후 백업」이다. §6 3항의 이유(pause 는 제출을 안 막으므로 확인과 정지 사이를 짧게)가 있어 문서가 맞다고 봤다. 결정 80 의 요약 줄을 §6 에 맞추는 것은 오너 몫(문서 한 줄).
