## FAIL 요약 (심각도 순: 보안 > fail-open > 기능 > 문서/문구)

보안·fail-open 급 결함은 찾지 못했다. 아래는 PARTIAL 로 판정한 항목의 결함이다.

### 기능

1. **미지원 HTTP 메서드가 JSON 405 가 아니라 stdlib HTML 501 페이지로 나간다** (G6 · H8). 재현: `curl -s -X DELETE http://127.0.0.1:PORT/api/status` → `HTTP/1.1 501 Unsupported method ('DELETE')`, `Content-Type: text/html`, `BaseHTTPRequestHandler` 의 기본 HTML(`Error code: 501`). `PATCH`·`OPTIONS` 도 같다. 스택·경로는 없지만 PLAN 「405/400/… 명확히 · 예외는 500 한 줄」·「오류 응답은 JSON」과 어긋난다. 책임: `src/remote_ci_monitor/server.py` `Handler` — `do_GET = do_POST = do_PUT = do_HEAD = _dispatch` 만 있고 그 밖의 메서드에 대한 처리(예: `do_DELETE`/`do_OPTIONS`/`do_PATCH` → `ApiError(405)`)가 없다.
2. **`rcm wait --timeout N` 이 서버 불통 중엔 N 을 무시하고 60초를 다 기다린다** (B2). 재현: 서버를 내린 뒤 `rcm wait --job 1 --timeout 3` → `exit=3 after 60s: lost contact with the server`. 종료 코드 3 은 맞으나 PLAN 「`--timeout` 초과 3」이 「연결 실패 60초 → 3」보다 늦게 적용된다. 책임: `src/remote_ci_monitor/client.py` `_poll_for_job` — timeout 검사가 성공한 조회 뒤에만 있고(603 행), 불통 분기(586–597 행)엔 `CONNECTION_GRACE_SECONDS` 만 본다. `wait_for_job` 의 SSE 루프도 같다.

### 문서/문구

3. **업로드 포기 summary 가 60초 미만 설정이면 `upload abandoned after 0m`** (B3). 재현: `upload_abandon_seconds = 45` → 45초 뒤 `cancelled`, summary `upload abandoned after 0m`. 책임: `src/remote_ci_monitor/store.py` `abandon_stale_uploads` — `mins = int(abandon_seconds // 60)`. 기본 300 이면 `5m` 으로 PLAN 문구와 같으나 분 미만은 `Ns` 로 찍어야 한다.

## PLAN 이 구현과 다른데 구현이 맞는 경우 (PLAN 을 고쳐야 하는 항목)

1. **tar 절대 경로 (E4)**: PLAN 「`tarfile.extractall(filter="data")` — 절대 경로·`..`·바깥 링크·장치 파일을 거부」. 실제 Python data 필터는 선행 `/` 를 떼어 **상대 경로로 바꿔 워크스페이스 안에 푼다**(`/tmp/x` → `<ws>/tmp/x`, 관찰됨) 그리고 그래도 절대인 경우(`C:/…`)만 `AbsolutePathError`. 탈출은 없으므로 안전하다. PLAN 문구를 「절대 경로는 상대화, `..`·바깥 링크·장치 파일은 거부」로 고친다. (엄격히 거부하고 싶다면 `materialize.extract_tree` 에서 `member.name.startswith("/")` 를 직접 막아야 한다 — 선택.)
2. **chunked/Content-Length 없음 → 411 (H2)**: 체크리스트 기대는 400, PLAN 은 「chunked 거부」로만 적혀 있다. 구현은 `411 Length Required`(`server.py:1025–1028`, 서버 docstring 도 411) — HTTP 의미상 맞다. PLAN 「hardening」 줄에 411 을 명시하고 체크리스트 H2 기대를 411 로 바꾼다.
3. **종료 잡의 `GET /jobs/{id}` 에 `log_tail` 키가 없다 (H3)**: PLAN 「아니면 null」. 구현은 종료 잡을 recent 행 모양(`recent_json`)으로 돌려주고 그 모양엔 `log_tail` 이 원래 없다(PLAN 스키마 예시의 recent 도 없음). 「종료 잡은 recent 행 모양(log_tail 없음)」으로 적는다.
4. **선행 `//` 경로 (H8)**: `http.server` 가 요청 줄 파싱 단계에서 `//api/status` → `/api/status` 로 접기 때문에 라우터의 `"//" in path → 400` 은 중간 `//` 에만 걸린다. 무해하며 `..` 탈출은 400 으로 막힌다. 체크리스트 H8 의 「`//` 경로 → 400」 기대를 「`/a//b` 400, 선행 `//` 는 stdlib 정규화」로 바꾼다.
5. **워크스페이스 보존 범위 (E8)**: PLAN 「`keep_workspace_on_failure = true` 면 실패는 보존」. 구현은 `state != succeeded`(failed·timed_out·cancelled·lost) 전부 보존(`worker.py:321`). 디버깅에 유용하니 구현대로 「성공이 아닌 잡」으로 적는다.
6. **F3 「전부 실패면 `hosts_error`」**: macOS 에선 `os.getloadavg()` 가 libc 호출이라 명령이 전부 없어도 load 가 남아 표본이 만들어진다(칸별 null). `hosts_error` 는 수집기 예외 때만 나온다. PLAN 문구는 틀리지 않았으나 「macOS 에선 load 가 항상 있어 칸별 null 이 일반적」이라고 덧붙이면 오해가 없다.

## 확인 못 한 항목과 이유

- **F1 의 `kill -STOP` 방식**: 서버 프로세스를 멈추면 HTTP 도 멈춰 stale 을 조회할 수 없고, CONT 직후엔 샘플러가 먼저 새 표본을 만든다. 가짜 `top` 으로 주기를 늘려 같은 규칙(3×interval)을 검증했다.
- **F3 「전부 실패 → `hosts: null` + `hosts_error`」**: macOS 에서 재현 불가(위). 코드 `hostsample.sample_once` 206–213 행만 읽음.
- **H5 `reset`·`lag` 이벤트**: 링 버퍼(2048) 밖 `Last-Event-ID` 나 구독자 큐 넘침을 만들지 않았다. `events.py` 107–122 · 53–73 행 코드 읽기.
- **H7 janitor 죽음 → 503**: DB 오류를 주입하지 않았다. `janitor._loop` → `dead` → `App.health()` 503 코드 읽기.
- **H8 「예외는 500 한 줄」**: 500 을 유발할 안전한 방법이 없어 코드(`server.py:1005–1012`)만 읽음.
- **E10 `materializing` 을 `/api/status` 폴링으로 직접 캡처**: 60MB 트리도 추출이 50ms 미만이라 못 잡음. `rcm run` 의 `preparing workspace` 줄(= `GET /jobs/{id}` 의 `phase: materializing`)로 대체.
- **C7 `high`(n≥5)**: 같은 키 성공 5회를 쌓지 않았다. `core/queue.confidence` 코드.
- **D5 함정 2(마지막 스텝 끝 = 잡 종료)**: 종료 잡엔 steps 가 안 실려 API 로 못 본다. `tests/test_progress.py:55` 와 `progress_from_markers(finished_at=…)` 로 확인.
- **B3(a) 실제 512MB 초과 트리**: `max_snapshot_bytes = 1000` 으로 대체.
- **Linux 쪽(A5 · F2 · F3 의 `/proc`·`nvidia-smi` 경로)**: macOS 한 대에서만 검사. 픽스처 테스트(`tests/test_hostparse.py`)는 있으나 실기는 오너/CI 몫.
- **A6 `pipx install`**: pipx 가 있었지만 격리를 위해 같은 wheel 을 새 venv 에 설치해 확인.
- **B4 뒤 고아 자식 프로세스**: `kill -9` 뒤엔 프리셋 자식(`sleep 300`)이 살아남는다. PLAN 이 요구하는 항목은 아니라 판정에 넣지 않았고 README 런북 후보로만 적는다.
