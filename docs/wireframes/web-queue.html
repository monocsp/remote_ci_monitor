서버 신원과 워커 v1.3

보여주는 것
제품 이름, 빌드 머신 이름, lanes 2/2 busy, 레인마다 지금 도는 잡 id.
데이터
hosts[0].name · lanes · server.workers[].{lane, state ∈ idle|busy|down, job_id, error, since} · server.paused · server.last_error.
상태
busy 파란 점 + 잡 id · idle 회색 점 · down(빨간 네모 + lane 1 · down, 27) · paused(황토 두 줄, 28). server.last_error 가 있으면 빨간 error · <앞 60자> 칩(클릭 시 전체) gap. 레인 1 이면 필 하나로 접는다(worker busy #412).
상호작용
잡 id 는 버튼 — 누르거나 Enter 로 그 큐 행으로 스크롤하고 잠깐 강조.
규칙
워커가 죽었는데 큐만 멀쩡해 보이는 화면이 가장 위험하다 — 죽음·정지·마지막 오류는 머리에서 보여야 한다.

갱신 상태 토글 v1.3

보여주는 것
버튼 하나: ● live · updated 4s ago. 누르면 paused · resume(회색 점) — 로그를 읽는 중 행이 튀지 않게 ref(Sidekiq Live Poll). 탭이 60초 넘게 숨겨지면 자동 정지, 돌아오면 /api/status 를 다시 받는다.
데이터

상태
live(SSE) → SSE 가 끊기면 polling(10초 고정, 재연결은 2s→30s 백오프) → 30초 무응답이면 18 번 띠. 브라우저와 서버 시계가 30초 넘게 어긋나면 옆에 clock +2m 칩, 모든 상대 시간은 generated_at 기준으로 보정 gap. 재조회에서 uptime 이 줄면 Server restarted at 09:58 — running jobs were marked lost 띠, schema_version·server.version 이 바뀌면 UI out of date — reload(자동 새로고침 1회).
규칙
나이는 거칠게(4s ago → 60초 넘으면 3m ago). lost 는 잡 결과에만, 연결엔 Lost connection.

안 움직이는 것 v1.3

보여주는 것
행동할 수 있는 원인만, 「행동 가능」 순으로: 워커 다운 → likely stuck → 업로드 멈춤 → 스케줄 안 됨 → 그룹 대기 → 초과 실행 → 정지 ref. 각 줄에 근거 숫자(frees in 2m 40s, over by 3m 31s).
데이터
queue[].reason ∈ {blocked_by_group, upload_stalled, overdue, paused, not_scheduled, worker_down} · estimate.stuck · blocked_by.remaining_seconds · server.workers[].state.
상태
없으면 초록 Nothing is stuck. 하나라도 있으면 그 아래 회색 nothing else is stuck. queue_error → 회색 unknown — queue unavailable. 연결 끊김(18) → 회색 last known: + dim. reason 필드가 없는 옛 서버 → unknown gap.
규칙
긍정 문구는 조회가 성공했고 값이 전부 있을 때만. 정상 대기(waiting for lane)와 스텝이 실패했지만 계속 도는 잡은 여기 안 올린다.

4. 이 화면이 정한 규칙

  • 표기 gap·ref: 시각은 HH:MM(오늘이 아니면 Sep 3 · 23:40). 소요·잔여·대기는 한 함수로 12s · 5m 10s · 1h 02m, 모름은 —, 앞에 맥락 단어(in · waiting · waited · over by · stale · frees in). 나이·카운트다운은 거칠게(4s ago, 60초 넘으면 3m ago, in 8s). 퍼센트 정수, 메모리 GB 소수 한 자리·MB 정수·단위 앞 공백(500 MB), 표본 n=7, id #412, 순번 2nd in line. 라벨은 40자 절단 + 툴팁.
  • 갱신: 처음 GET /api/status, 이후 SSE 부분 갱신. SSE 재연결 2s→30s 백오프, 그 사이 폴링 10s 고정, 30s 무응답이면 18. 경과·대기·나이는 generated_at 으로 보정한 클라이언트 시계로 1초마다. 탭 숨김 60s → 정지, 복귀 → 재조회. 2 번 토글로 수동 정지.
  • 정렬·많은 잡: running → cancelling → 대기(순번순). 필터 없음. 대기 20행 넘으면 접고 내 잡·안 움직이는 잡은 항상 표시. 최근 완료는 시간 역순 5건 + 더 보기.
  • 펼침·딥링크 gap: 실행 중 행은 전부 펼침, 접힘은 잡 id 별 localStorage(큐에 없는 id 는 매 갱신 정리). #/jobs/<id> = 그 행 스크롤·강조·펼침(+토큰 있으면 서랍); 큐에 없으면 최근으로, 거기도 없으면 토스트 #409 finished 09:55 · succeeded. 서랍 열림도 해시(뒤로가기 = 닫기).
  • 권한: 보기는 토큰 없이. 내 잡 강조·로그 tail·로그·취소만 토큰. 여러 탭은 storage 이벤트로 토큰 동기화.
  • 실패 표시: 섹션마다 독립 — 큐(22)·최근(32)·호스트·연결(18)·워커(27)가 따로 실패한다. 실패와 빈 값은 항상 다른 모양. 긍정 문구(Nothing is stuck·fine)는 조회 성공 + 값 완전일 때만. 큐에서 사라지는 잡은 없다 — 전부 종료 상태로 최근에 남는다.
  • 상태 부호화: 색 + 글리프 + 테두리. 빗금 = 낡음/멈춤, 점선 테두리 = 미확정(uploading·cancelling·timed out·low 신뢰도·blocked), 왼쪽 굵은 황토 바 = 초과 실행, 왼쪽 가는 파란 선 = 내 잡(둘 다면 겹쳐 그린다), 회색 = 대기·취소, 빨강 = 실패·타임아웃·stuck·다운, 보라 = lost. 단색 인쇄에서 읽히는지가 수용 기준.
  • 키보드·보조기기 gap: 행 펼침 ▾, 잡 id, 칩, sha, Log, Cancel, show more, Estimates, live 토글은 전부 button/summary. Tab 순서는 읽는 순서, Enter/Space 동작, 포커스 링 파랑 2px. 글리프는 aria-hidden. aria-live="polite" 는 상태 전이(내 잡 시작·종료·lost, 연결 끊김/복구)만, 초당 갱신 요소는 off. 띠(18·22·27·32)는 role="alert". 진행 막대 role="progressbar", 호스트 막대 <meter>.
  • 시간: 모든 시각은 UTC 로 받아 3 번 시간대로. 상대 시간은 보정된 브라우저 시계.

5. PLAN 반영 제안

  • 잡 모델: 상태 cancelling 추가. 업로드 포기·413·tar 거부·claim 시 프리셋 소멸은 잡을 지우지 않고 cancelled/failed + summary(exit_code: null 허용).
  • 큐 규칙: position 은 대기 잡에만 1부터, 실행 중·취소 중은 null. 대기 계산은 state ≠ down 레인 수로 하고 0 이거나 paused 면 finish_at·wait_seconds 는 null. 그룹에 막힌 잡은 finish_at ≥ 막는 잡 finish_at + expected. 합류자는 joiners[] 에 남기고 화면·rcm jobs --mine 은 요청자와 합류자를 모두 「내 잡」으로. 원 요청자의 취소는 합류자에게 종료 코드 2 로 전파. 신뢰도 규칙(n≥5 high · n<5 med · preset/default low). stuck_multiplier(3)·no_output_seconds(240).
  • 스키마: server.{paused, workers[].{state, job_id, error, since}, last_error} · queue[].{position, reason, lane, ahead_job_id, concurrency_group, joiners[], cancel, blocked_by.remaining_seconds} · source.{received_bytes, last_received_at} · estimate.{waited_seconds, stuck} · progress.{phase, last_output_at, steps[].ok} · recent[].{waited_seconds, cancelled_by, timeout_seconds, started_at, inputs, transitions[]} · medians[key].wait_seconds · presets[].{expected_seconds, timeout_seconds} · hosts[].{interval_seconds, memory.compressed, history[]}. recent_error·medians 도 「null + 오류」 규칙. log_tail 은 유효 토큰 요청·running 잡에만.
  • API·CLI: GET /api/whoami, POST /pause·/resume(admin), rcm pause|resume. GET /jobs/{id} 의 log_tail 도 토큰 조건.
  • 설정: [server] recent_count = 8 · upload_stall_seconds = 60 · upload_abandon_seconds = 300, [estimate] stuck_multiplier = 3 · no_output_seconds = 240, [host] history_samples = 60.
  • 웹 UI (M2) 절: ASCII 스케치를 지우고 「배치·상태·문구·표기 규칙은 docs/wireframes/web-queue.html 이 정본. 큐 위에 Your jobs · Not moving · Host pressure 요약을 먼저」. 갱신 규칙(SSE 2→30s 백오프 · 폴링 10s · 30s 무응답 띠 · 시계 보정 · 버전 불일치 새로고침). 완료 기준 「서버를 끊으면 stale」 → 「서버를 끊으면 Lost connection 띠가, 샘플러만 멈추면 stale 배지가 뜬다」.
  • fail-open 금지: 「요약 줄의 긍정 문구는 해당 섹션 조회가 성공했고 값이 전부 있을 때만 그린다」 「큐에서 조용히 사라지는 잡은 없다」.
  • 결정 항목: 6절의 질문 5개를 ⛔ 로 올린다(현재 「열린 ⛔ 없음」과 모순).
