웹 큐 화면

빌드 머신 한 대의 큐·진행·자원·최근 결과를 한 화면에 보여주는 첫 화면이다. 목업은 /api/status 스키마 v1 의 실제 필드 값으로 그렸고, 오른쪽 번호는 그 요소의 기획 항목 번호다. 번호나 항목에 마우스를 올리면 서로 강조되고, 번호를 누르면 항목으로 이동한다.

1 기획 항목 번호 요소를 가리키는 선UI 문자열은 영어(제품 규칙), 설명은 한국어레인 2 로 그렸다 — 그룹 대기를 보이기 위해

v1.2 (Codex 디자인 리뷰 반영, docs/reviews/2026-09-04-codex-web-queue.md): 첫 화면의 질문 「내 잡은 몇 번째, 언제 끝나나, 왜 안 움직이나」에 5초 안에 답하도록 큐 위에 요약 줄(23·24·25)을 올리고, Reason 열(11)을 만들고, 열 순서를 바꾸고(소스는 맨 뒤), Remaining 과 ETA 를 합치고, 경고색 하나에 몰려 있던 상태들을 모양으로 갈랐다. 타임라인은 세로 목록이 기본이 됐고 호스트 카드가 최근 완료 위로 올라왔다. 변형 상태 6개(26~31)를 더했다.

서버 신원과 워커

보여주는 것
제품 이름, 빌드 머신 이름, 레인 수, 레인마다 지금 도는 잡 번호.
데이터

상태
busy 파란 점 + 잡 번호 · idle 회색 점 · down(빨간 네모 + lane 1 · down, 27) · paused(황토 두 줄, 28). 레인 1 이면 필 하나로 접는다(worker busy #412).
상호작용
잡 번호는 버튼 — 누르거나 Enter 로 그 큐 행으로 스크롤하고 잠깐 강조.
규칙
워커가 죽었는데 큐만 멀쩡해 보이는 화면이 가장 위험하다 — 죽음·정지는 머리에서 보여야 한다.

갱신 상태와 나이

보여주는 것
연결 방식(live = SSE, polling)과 마지막으로 새 데이터를 받은 지 몇 초인지.

Reason 열 v1.2

보여주는 것
이 잡이 지금 왜 이 상태인지 한 칸에: running · lane 1 · waiting for lane · behind #412 · ⛓ blocked by #409 · devices(황토 점선 테두리) · uploading · 30 / 48 MB · upload stalled 2m(빗금 배경, 31) · over by 3:31 · delays #4(20) · paused(28).
데이터
reason ∈ {running, waiting_for_lane, blocked_by_group, uploading, upload_stalled, overdue, paused} · blocked_by · ahead_job_id(바로 앞에서 밀고 있는 잡).
상태
행동 가능한 이유(blocked·stalled·overdue·paused)는 진한 글자와 모양, 정상(running·waiting)은 회색 글자. 레인 1 이면 blocked 는 절대 안 나온다.
상호작용
잡 번호는 링크 — 막고 있는 잡·앞선 잡 행으로.
규칙
「왜 안 움직이나」는 표를 해석해서 알아내는 게 아니라 읽는 것이어야 한다. 이 열은 스키마에 reason 필드를 요구한다(PLAN 반영 제안).

경과 · ETA v1.2

보여주는 것

진행 — 스텝 목록 v1.2

보여주는 것
실행 중 행은 기본으로 펼쳐진다. 머리 step 5/8 · test · 51s · job 59s, 그 아래 얇은 요약 막대(라벨 없음, 스텝 소요 비례), 본체는 세로 목록(두 열): ✔ analyze 12s · ▶ test 51s(파랑) · · build-web(회색).

4. 이 화면이 정한 상호작용 규칙

  • 갱신: 처음 GET /api/status, 이후 GET /events(SSE) 부분 갱신. 경과·대기·나이는 클라이언트 시계로 1초마다 올리고 서버 값이 오면 덮어쓴다.
  • 정렬·필터: 큐는 상태(running → cancelling → uploading/queued) → 순번 고정. 필터 없음. 최근 완료는 시간 역순 5건 + 더 보기.
  • 펼침: 실행 중 행은 전부 자동 펼침, 접힘은 잡별로 localStorage 에 기억. 대기 행은 펼칠 것이 없다.
  • 권한: 보기는 토큰 없이. 내 잡 강조·로그 tail·로그·취소만 토큰. 토큰은 localStorage, URL 금지, 화면엔 이름만.
  • 실패 표시: 섹션마다 독립 — 큐(22)·호스트(hosts_error)·연결(18)·워커(27)가 따로 실패하고 나머지는 계속 보인다. 실패와 빈 값은 항상 다른 모양.
  • 상태 부호화: 색 + 글리프 + 테두리 모양. 빗금 = 낡음/멈춤, 점선 테두리 = 미확정(uploading·cancelling·low 신뢰도·blocked), 왼쪽 굵은 바 = 초과 실행, 왼쪽 가는 파란 선 = 내 잡.
  • 키보드: 행 펼침 ▾, 잡 번호, Log, Cancel, show more, Estimates 는 전부 button/summary 이고 Tab 순서는 읽는 순서, Enter/Space 로 동작, 포커스 링은 파랑 2px.
  • 시간: 모든 시각은 UTC 로 받아 3 번 시간대로 그린다. 상대 시간(4s ago)은 브라우저 시계 기준.

5. PLAN 반영 제안

  • queue[].reason 필드를 스키마에 넣는다: running · waiting_for_lane · blocked_by_group · uploading · upload_stalled · overdue · paused. UI 가 표를 해석하지 않고 읽게(11·24).
  • /api/status 와 GET /jobs/{id} 의 log_tail 은 유효한 토큰 요청에만 싣고 없으면 null(13).
  • GET /api/whoami 라우트(토큰 → {name, admin})(4). rcm check 도 같은 걸 쓴다.
  • server.workers[].{state, job_id, error} 와 server.paused.{by, at} 을 본문에 설명하고(1·27·28), 잡 상태에 cancelling 을 추가한다(30).
  • source.received_bytes 와 서버 설정 upload_stall_seconds(60)·upload_abandon_seconds(300)(6·31).
  • M2 웹 UI 절에 「큐 상단에 Your jobs · Not moving · Host pressure 요약을 먼저 표시한다. 토큰이 없으면 Your jobs 는 토큰 안내만」을 넣는다(23·24·25).
  • Apple Silicon GPU 메모리는 total 이 없으므로 비율 막대를 그리지 않고 memory in use N GB 텍스트로만(16).

6. 오너에게 묻는 것 Codex 추천 병기

  • 레인 1 인 서버(지금의 Mac mini)에선 워커 필을 하나로 접고 Reason 의 blocked 는 자연히 안 나온다 — 이대로 가나? 추천: 예. 레인 1 에서 그룹 대기는 사용자가 행동할 수 있는 원인이 아니다.
  • 실행 중 행이 여러 개일 때 전부 펼치나? 추천: 전부. 레인 2 이상에서 어느 잡이 막혔는지 비교해야 한다. 접힘만 기억.
  • 최근 완료는 8건(설정 recent_count)인가 24시간인가? 추천: 8건. 시간 기준은 조용한 서버와 바쁜 서버에서 정보량이 너무 다르다.
  • 토큰 입력(4·13·23)을 M2 에 넣나? 추천: 넣는다. 폰에서 로그 확인과 취소가 실제 운영 행동이다.
