3. 기획 항목

각 항목은 「보여주는 것 · 데이터(스키마 필드) · 상태 · 상호작용 · 규칙」 순이다. 규칙은 PLAN.md 의 fail-open 금지·보안 절과 맞물린다. 스키마 필드는 pools[0] 기준이다.

머리 — 서버와 연결
1
header

서버 신원과 워커

보여주는 것
제품 이름, 빌드 머신 이름, 레인 수, 레인마다 지금 도는 잡 번호. 한눈에 「지금 몇 개가 동시에 도나」.
데이터
hosts[0].name · lanes · server.workers[].{lane, state, job_id}
상태
busy 는 파란 점 + 잡 번호, idle 은 회색 점 + idle. 워커 스레드가 죽었으면(server.last_error) 점 대신 경고색 worker down 과 사유.
상호작용
잡 번호를 누르면 그 큐 행으로 스크롤하고 잠깐 강조.
규칙
레인 수는 설정값이라 「추정」이 없다. 워커가 죽었는데 큐만 멀쩡해 보이는 화면이 가장 위험하다 — 죽음은 머리에서 보여야 한다.
2
header

갱신 상태와 나이

보여주는 것
연결 방식(live = SSE, polling)과 마지막으로 새 데이터를 받은 지 몇 초인지.
데이터
클라이언트가 /events 로 마지막 이벤트를 받은 시각(브라우저 시계) 과 generated_at.
상태
live(초록 점) → SSE 가 끊기면 10초 폴링으로 내려가며 polling(회색 점) → 30초 넘게 아무것도 못 받으면 18 번 배너.
규칙
화면이 멈췄는데 숫자가 그대로면 사람은 모른다. 나이는 1초마다 올라가야 하고, 이 칸이 없는 상태로 배포하지 않는다.

header

시간대

보여주는 것
화면의 모든 시각을 어느 시간대로 그리는지. 서버 설정이 있으면 그 IANA 이름, 없으면 브라우저 로컬을 쓰고 (browser) 를 덧붙인다.
데이터
display_timezone(null 이면 브라우저) · 모든 시각 필드는 UTC ISO-8601 로 와서 Intl.DateTimeFormat 으로 변환.
상호작용
없음. 바꾸려면 서버 설정 display.timezone. 툴팁에 「set display.timezone on the server to pin this」.

header · auth

토큰 입력

보여주는 것
읽기 전용으로는 필요 없다. 로그 tail·로그 보기·취소를 하려면 자기 토큰을 붙여넣는다. 붙여넣은 뒤엔 토큰 값이 아니라 토큰 이름(alice-laptop ✓)만 보인다.
데이터
GET /api/whoami(토큰 → 이름·admin 여부). 토큰은 localStorage 의 rcm.token 에만 저장하고 URL·쿼리에 절대 싣지 않는다.
상태
없음(add token 링크) · 유효(이름 ✓) · 거부(401 → 빨간 테두리 + Token rejected, 저장값 삭제).
규칙
토큰이 없어도 화면 전체가 읽힌다(읽기 none 전제). 토큰이 있을 때만 13 번 액션과 로그 tail 이 켜진다.

큐 헤더

보여주는 것
활성 잡 수와 상태별 분포. 「대기가 몇 개인가」를 표를 세지 않고 알게.

queue[] 의 state 집계.
규칙

순번과 상태

보여주는 것
FIFO 순번과 상태 필. ▶ running(파랑) · · queued(회색) · ↑ uploading(회색, 세션이 아직 트리를 올리는 중).
데이터
position · state. uploading 은 8 번 소스 칸에 받은 바이트 / source.bytes 진행 막대.
상태
uploading 잡은 순번은 받았지만 큐에 「확정」되지 않았다. 업로드가 끊기면 5분 뒤 서버가 지우고 행이 사라진다(이벤트로 알림).
규칙
실행 중인 잡은 항상 대기 잡보다 위다(순번은 생성 순, 정렬은 상태 → 순번).

키·프리셋·입력

보여주는 것
소요시간 버킷인 key(굵게)와 입력값 칩. 그룹이 있는 프리셋은 group devices 칩.
데이터
key · preset · inputs · 프리셋의 concurrency_group(presets[] 에서 조인).
상호작용
키를 누르면 15 번 중앙값 줄에서 같은 키를 강조. 입력 칩 툴팁에 전체 입력 JSON.
규칙
키는 「같은 키끼리 비교한 예상」임을 툴팁에 밝힌다(estimates compare jobs with the same key).

queue · row

소스

보여주는 것
어떤 코드가 도는지. tree 모드는 base_sha 7자리 + 미커밋 변경이 있으면 +dirty(황토), 아래에 레포 이름. git_ref 모드는 sha · ref dev.
데이터
source.{mode, base_sha, dirty, tree_hash, repo, ref, sha, bytes}.
상호작용
sha 툴팁에 전체 sha 와 tree_hash. 같은 tree_hash 인 행은 hover 시 같이 강조(같은 코드를 두 사람이 올렸다는 뜻 — 보통은 합류돼서 한 행이지만 --no-join 이면 둘 다 보인다).
규칙
+dirty 는 「푸시된 커밋과 다르다」는 신호라 눈에 띄어야 한다. 배포 프리셋(git_ref) 행에는 dirty 가 절대 없다.

hover 시 같은 요청자의 다른 행을 같이 강조. 내 토큰(4)과 같은 이름이면 you 배지.

라벨은 외부 입력이라 40자에서 자르고 제어문자를 지운다(서버가 이미 하지만 UI 도 escape).

경과 · 잔여 · 예상 완료

보여주는 것
running 은 경과(0:59) · 잔여(5:10) · ETA(09:57). queued 는 waiting 1:35(생성 후 대기) · 잔여(앞선 잡 포함 안 함, 자기 소요만) · ETA(앞선 잡 잔여 누적). ETA 아래 작은 글씨로 근거: measured · n=7 / preset / default.
데이터
estimate.{elapsed_seconds, remaining_seconds, wait_seconds, finish_at, source, sample_count, overdue} · created_at · started_at.
상태
source 가 preset/default 면 이탤릭 회색(신뢰도 낮음). overdue 면 20 번 처리. 경과·대기는 1초마다 클라이언트에서 증가시키되 서버 값이 오면 덮어쓴다.
규칙
잔여 하한 30초는 계산 규칙이라 「곧 끝난다」가 아니라 「예상보다 오래 걸리고 있다」로 읽히게 20 번으로 넘긴다. 모르는 값(null)은 — 로 그리고 0 으로 그리지 않는다.

그룹 대기

보여주는 것
레인이 비어 있는데 concurrency 그룹이 겹쳐 못 올라간 잡. blocked by #409 · devices.
데이터
blocked_by.{job_id, group}.
상태
레인 1 인 서버에선 절대 뜨지 않는다(한 번에 하나만 도니까). 이 열은 값이 하나도 없으면 통째로 숨긴다.
상호작용
누르면 막고 있는 잡 행으로.
규칙
대기 사유가 「앞에 줄이 길어서」인지 「장비를 같이 써서」인지는 사용자에게 다른 정보다 — 섞지 않는다.

queue · expanded

진행 — 스텝과 타임라인

보여주는 것
실행 중 행은 기본으로 펼쳐진다. 머리에 step 5/8 · test · 51s · job 59s. 아래 타임라인은 스텝마다 막대 하나: 끝난 스텝 초록(길이 = 소요 비례, 최소 폭), 진행 중 파랑(조금 높게), 아직 안 온 스텝 점선.
데이터
progress.{steps_total, steps_total_partial, steps_done, current_index, current_name, current_seconds, job_seconds, steps[], timing}.
상태
steps_total_partial 면 5/8 (so far). 마커가 하나도 없으면 타임라인 대신 no step markers · job 59s 한 줄. 잡이 queued 면 이 블록 자체가 없다(0/0 금지).
상호작용
막대 hover 에 스텝 이름·소요. 행 머리의 ▾ 로 접고 펼침(접은 상태는 localStorage 에 기억).
규칙
timing: as_received — 스텝 시각은 서버가 마커를 받은 시각이라 출력 버퍼링 때문에 늦을 수 있다. 머리 옆 ⓘ 툴팁에 그 문장을 그대로 쓴다.

queue · expanded · auth

로그 tail 과 액션

보여주는 것
로그 마지막 3~5줄과 Log·Cancel 버튼.
데이터
log_tail — 토큰이 있는 요청에만 실린다(없으면 null). Log 는 GET /jobs/{id}/log?offset= 증분 스트림을 옆 서랍(drawer)에 연다. Cancel 은 확인 뒤 POST /jobs/{id}/cancel.
상태
토큰 없음 → tail 자리에 Add a token to see the log, 버튼 비활성. 내 잡이 아니고 admin 도 아니면 Cancel 비활성 + 툴팁 not your job. 취소 요청 뒤엔 버튼이 cancelling… 으로 바뀌고 상태 이벤트로 확정.
규칙
로그엔 시크릿이 섞일 수 있어 읽기 none 이어도 로그만은 토큰 필수(PLAN 「보안」). 이 항목은 PLAN 의 /api/status 스키마에 「log_tail 은 토큰 요청에만」을 추가해야 한다 — 아래 「PLAN 반영 제안」.

최근 완료

보여주는 것
최근 8건. 결과 필(✓ succeeded · ✗ failed + exit code · ⏹ cancelled · ⏱ timed out · ? lost) · 키 · 요청자 · 소요 · 끝난 시각 · 요약 한 줄(summary) 과 실패 스텝.
데이터
recent[].{state, exit_code, key, requester, job_seconds, finished_at, summary, failed_step}.
상태
lost 는 사유 server restarted while running. cancelled 는 누가 취소했는지. timed_out 은 한계값과 죽은 스텝.
상호작용
행을 누르면 잡 상세(로그 서랍, 토큰 필요). 결과 필을 누르면 같은 결과만 필터(선택).
규칙
표본 정책(성공만)과 무관하게 전부 보인다. 걸려서 죽은 잡은 그 자체가 신호다.

호스트 카드

보여주는 것

값은 폴링(기본 5초)이라 「실시간」이 아니라 「N초 전」임을 나이로 항상 보인다.

연결 끊김 배너

보여주는 것
SSE 도 폴링도 30초 넘게 실패하면 화면 맨 위에 황토색 띠: Lost connection to macmini · last update 42s ago · showing last known state, 아래에 reconnecting in 8s…. 2 번 점은 회색.
상태
지수 백오프(2s → 30s)로 재연결. 돌아오면 띠가 사라지고 전체 상태를 /api/status 로 한 번 다시 받는다.
규칙

4. 이 화면이 정한 상호작용 규칙

  • 갱신: 처음에 GET /api/status 한 번, 이후 GET /events(SSE)로 큐·진행·호스트 이벤트를 받아 부분 갱신. 경과·대기·나이는 클라이언트 시계로 1초마다 올리고 서버 값이 오면 덮어쓴다.
  • 정렬·필터: 큐는 상태(running → uploading/queued) → 순번 고정. 필터 없음. 최근 완료도 시간 역순 고정. 검색·필터는 M2 범위 밖.
  • 펼침: 실행 중 행은 전부 자동 펼침. 사용자가 접으면 그 잡은 접힌 채 유지(localStorage). 대기 행은 펼칠 것이 없다.
  • 권한: 보기는 토큰 없이. 로그 tail·로그·취소만 토큰. 토큰은 localStorage, URL 금지, 화면엔 이름만.
  • 실패 표시: 섹션마다 독립 — 큐(22)·호스트(hosts_error)·연결(18) 이 따로 실패하고 나머지는 계속 보인다. 실패와 빈 값은 항상 다른 모양.
  • 시간: 모든 시각은 UTC 로 받아 3 번 시간대로 그린다. 상대 시간(4s ago)은 브라우저 시계 기준.

5. PLAN 반영 제안

  • /api/status 의 log_tail 은 토큰이 있는 요청에만 싣고 없으면 null 로 한다(13). 「로그는 항상 토큰」 규칙과 스키마 예시가 지금은 어긋난다.
  • GET /api/whoami 라우트를 추가한다(4). 토큰 → {name, admin}. 클라이언트 rcm check 도 같은 걸 쓴다.
  • server.workers[] 를 스키마에 넣는다(1). 지금 예시엔 있지만 본문 설명이 없다.
  • uploading 잡의 수신 바이트를 source.received_bytes 로 싣고, 업로드가 끊긴 잡의 정리 시간(5분)을 설정에 둔다(6).
  • 이 화면은 M2 를 읽기 전용 + 토큰 액션으로 정의한다. 잡 상세(로그 서랍)는 별도 와이어프레임에서 그린다.

6. 오너에게 묻는 것

  • 레인 1 인 서버(지금의 Mac mini)에서는 1 번 워커 표시와 11 번 그룹 대기 열이 노이즈다. 레인 1 이면 워커 필을 하나로 접고 그룹 열은 숨기는 것으로 가도 되나?
  • 실행 중 행이 여러 개일 때 전부 펼치는 게 맞나, 첫 번째만 펼칠까? (제안: 전부, 접힘은 기억)
  • 최근 완료는 「8건」인가 「24시간」인가? (제안: 8건, 서버 설정 recent_count)
  • 토큰 입력(4·13)을 M2 에 넣을지, M2 는 읽기 전용으로 끝내고 로그·취소는 CLI 로 두고 M3 에서 넣을지. (제안: M2 에 넣는다 — 폰에서 취소하고 싶을 때가 있다)
